# Prime Mobile OS — архитектура

Версия 2 · 06.11.2026 · только проект, кода нет. Макеты экранов — в `docs/design/`.

Собственная система учёта для магазина мобильной техники Prime Mobile (Казахстан) на замену облачной Smartfon System (sfon.kz, 54 000 ₸/мес). Три части: ERP/склад/касса, сайт-витрина, позже Telegram-бот trade-in.

---

## 0. Коротко

- **Одно приложение на Laravel** на одном сервере в Казахстане: учёт, касса, витрина и бот — внутри него, но разделены на модули с чёткими границами.
- **Остатки и деньги нельзя «поправить руками».** Они считаются только из журнала операций. Ошибку исправляют обратной записью (сторно), старая запись остаётся.
- **Один IMEI нельзя продать дважды.** Это проверяет сама база данных, а не только программа.
- **Две фирмы в одной системе.** Prime Mobile (Кайрат) и второй филиал — отдельные фирмы: у каждой свои деньги, долги, клиенты и отчёты. Друг друга они не видят.
- **Витрина показывает каждый телефон отдельно** (своё фото, состояние, цена). IMEI, себестоимость, поставщики и клиенты на сайт не попадают никогда.
- **Вся история sfon переносится**, но как архив только для чтения. Живые остатки, долги и кассы стартуют с «входящих остатков» на дату переезда.
- **За 2 недели реально:** рабочая касса и склад первой фирмы на тестовом сервере с реальными остатками, готовые к параллельной работе с sfon. **Позже:** витрина, полная история, бот, отключение sfon (раздел 7).

## 1. Модули и их границы

Одно приложение (модульный монолит). Модуль — это папка с своими таблицами и правилами. В чужие таблицы модуль не пишет: просит владельца через его «действие» (например, «провести продажу»). Так проще проверять и позже вынести часть наружу.

| Модуль | Что делает | Чем владеет |
|---|---|---|
| **Доступы** | Фирмы, магазины, пользователи, роли, вход, 2FA | фирмы, магазины, пользователи, права |
| **Каталог** | Справочник: тип → семейство → модель, память, цвет, ОЗУ; аксессуары (артикул, штрихкод); фото моделей | справочники, варианты, аксессуары |
| **Склад** | Приход, поштучные телефоны (IMEI), аксессуары по количеству, перемещения, списания, ревизия сканером, возврат поставщику | экземпляры, журнал движения товара |
| **Касса (POS)** | Корзина, скан IMEI/штрихкода, оплата (нал/безнал/долг/сплит), сдача, клиент, trade-in в зачёт, доставка, источник, заказы, возврат покупателя | продажи, заказы, возвраты |
| **Деньги** | Счета (касса нал ₸, касса $, безнал, Kaspi и т.д.), расходы, инкассация, курс доллара | журнал денег, курсы |
| **Долги** | Долги клиентов и поставщикам, частичные оплаты, общий долг | журнал долгов |
| **Клиенты** | Карточка, поиск по имени и телефону, согласие на обработку данных, история покупок | клиенты |
| **Бонусы** | Начисление и списание, правила | журнал бонусов |
| **Trade-in** | Акт приёма б/у с ИИН продавца, оценка, сетка цен скупки; позже — заявки из бота | акты, сетка оценки, заявки |
| **Отчёты** | Выручка, себестоимость, прибыль, средний чек, возвраты, бонусы, остатки в деньгах, графики по дням и магазинам | только чтение + готовые сводки |
| **Печать** | Чек (нефискальный), гарантийный талон, накладная, акт trade-in, ценники и термоэтикетки — на казахском и русском | шаблоны |
| **Витрина** | Публичный каталог, карточка телефона, кнопка WhatsApp | публичная копия данных (только чтение) |
| **Бот trade-in** (позже) | Telegram: оценка телефона и заявка на скупку | сессии бота |
| **Интеграции** (позже) | Облачная касса (Webkassa / re:Kassa), Kaspi, ЭСФ, Open API sfon для сверки | очередь отправки, журнал обменов |
| **Перенос** | Импорт из sfon, ночная сверка, архив истории | промежуточные таблицы, архив |
| **Журнал действий** | Кто, что, когда, с какого устройства; вход, печать, экспорт | журнал аудита |

### Почему один Laravel, а не отдельный сайт

- Один сервер, одна база, один деплой — меньше всего ломается и дешевле поддерживать.
- Витрине не нужен API для синхронизации: она читает свою публичную копию данных в той же базе (раздел 4).
- Изоляция всё равно есть: витрина работает на своём домене, в своём пуле PHP-процессов и читает только публичную таблицу. Если сайт завалят трафиком, касса не тормозит.
- Отдельный сайт (Next.js и т.п.) имеет смысл, только если понадобится мобильное приложение или очень сложный фронт. Сейчас — нет.

### Стек и почему

| Часть | Выбор | Почему |
|---|---|---|
| Основа | Laravel (актуальная стабильная), PHP 8.4+ | Как вы предложили; много готовых пакетов, легко найти разработчика в РК |
| База | PostgreSQL 16+ | Транзакции, блокировки строк, частичные уникальные индексы (защита IMEI), триггеры против правки журнала |
| Админка ERP | Filament **3.x** | Склад, справочники, отчёты, документы. Ветка 3, потому что Filament 4 построен на Tailwind 4, а он не работает в Chrome 109 (Windows 7) |
| Касса (POS) | **Livewire** (не Inertia) | Тот же стек, что у Filament: один язык, без отдельной JS-сборки. Касса — это формы и списки, Livewire справится. Скан IMEI с USB-сканера = ввод с клавиатуры. |
| Витрина | Blade + Livewire точечно, Tailwind | Быстрые страницы для SEO, кэш целиком |
| Стили | **Tailwind 3.4** | Работает в Chrome 109+ (ноутбук на Windows 7) и в Safari на iPhone. Переход на Tailwind 4 / Filament 4 — когда в магазине не останется Windows 7, без переделки экранов |
| Шрифт | Onest (+ JetBrains Mono для IMEI) | Есть казахские буквы и ₸, читается на слабых экранах |
| Очереди | Redis + Horizon | Обновление витрины, фото, PDF, ночная сверка, уведомления |
| PDF | dompdf со шрифтом Noto Sans или DejaVu Sans | Есть казахские буквы и ₸ — **проверить в 1-й день**. Если не пройдёт — Gotenberg (Chromium в контейнере) |
| Этикетки | HTML-шаблон точного размера → печать из браузера | Работает с любым термопринтером через драйвер. Позже можно перейти на прямую печать командами TSPL/ZPL |
| Excel | Laravel Excel (PhpSpreadsheet) | Импорт из sfon и выгрузки |
| Права | spatie/laravel-permission + политики Laravel | Роли и проверки на каждом действии |
| Журнал действий | spatie/laravel-activitylog + свои записи | |

## 1а. Устройства и дизайн (решения от 06.11.2026)

**Устройства:**
- **Ноутбук в магазине — Windows 7 остаётся** (решение владельца). Последний браузер — Chrome 109. Поэтому Tailwind 3.4 и Filament 3, обязательная проверка каждого экрана в Chrome 109 на 1366×768.
- **Режим «старый ноутбук»** — настройка конкретного компьютера: текст не мельче 13 px, серый темнее, рамки контрастнее, без теней и анимаций. Раскладка та же, отдельной «старой версии» нет.
- **Риск Windows 7 снижаем:** на ноутбуке ничего не хранится, продавец без прав администратора, автовыход по простою, владелец с телефона отключает доступ этого компьютера.
- **Владелец — iPhone 17 Pro Max:** статистика, деньги, долги, заявки «разрешить / отклонить» (скидка сверх лимита, возврат), приход телефона сканером IMEI через камеру. Ставится на экран «Домой» как приложение (PWA).
- **Продавцы — iPhone 12 и новее:** мобильная касса («Продажа») со сканером камерой, автодобавлением, Trade-In, доставкой, источником, комментарием.

**Дизайн:**
- Свой стиль, код и дизайн sfon не копируем. Но **названия разделов как в sfon** (Статистика, Продажа, Склад, Долги, Баланс, Расходы) и привычные приёмы: автодобавление после скана (0,8 с), горячие клавиши (Trade-in F8, Оплатить F9, Возврат F10 — уточнено в ТЗ 01, п. 0.8, чтобы совпадало с sfon, где F9 = «Оплатить»), переключатель «Электроника / Аксессуары».
- **Цвет акцента — настройка фирмы.** По умолчанию синий; графит — вариант в настройках. У второго владельца позже будет свой цвет. Статусные цвета (зелёный / жёлтый / красный) общие.
- Светлая и тёмная тема. Фото товаров в кассе и на складе (из sfon или свои; в макетах — временные).
- Продавец после входа попадает сразу в «Продажу», «Статистика» — только у владельца.

## 2. Модель данных

### 2.1 Фирмы, аккаунты и роли (каждый владелец отдельно)

**Решение (06.11.2026):** на старте работает только филиал Кайрата — одна фирма, один магазин. Но база с первого дня разложена по фирмам, поэтому второй владелец подключается без переделки.

```
organizations — фирма = аккаунт владельца (Prime Mobile; позже — второй филиал)
  ├─ stores — магазины фирмы (сейчас 1: ТРЦ «Керуен»)
  ├─ roles — роли ЭТОЙ фирмы (Владелец, Админ, Продавец + свои, например «Старший продавец»)
  │    └─ role_permissions — галочки из общего списка прав
  ├─ memberships — кто работает в фирме: пользователь × роль × магазины
  ├─ settings — курс $, лимиты скидок, бонусы, реквизиты ИП/ТОО, тексты гарантии, логотип
  └─ все бизнес-данные: товары, продажи, деньги, долги, клиенты (organization_id в каждой строке)
users — люди: телефон, пароль, 2FA (один человек может быть в нескольких фирмах)
permissions — общий список прав системы (меняет только разработчик)
```

**Правила:**
- **Свой аккаунт.** У каждого владельца своя фирма, свой вход, свои сотрудники. Владелец сам приглашает людей и сам раздаёт роли.
- **Свои роли.** Роли хранятся внутри фирмы. Кайрат может создать «Старшего продавца», и у второго владельца этой роли не появится. При создании фирмы ей копируются три стандартные роли; дальше владелец меняет их как хочет. Роль «Владелец» удалить или урезать нельзя.
- **Права гибкие:** включено / выключено, а где нужно — с лимитом (например, «скидка до 5 000 ₸»). Всё сверх лимита уходит заявкой владельцу на телефон.
- **Изоляция:** глобальный фильтр по фирме в приложении + Row Level Security в PostgreSQL. Даже ошибка в коде не покажет чужие строки. Тесты «чужая фирма не видна» обязательны перед подключением второй фирмы.
- **Между фирмами ничего общего**, кроме справочника моделей (Д1). Остатки, клиенты, цены, деньги, сотрудники — раздельно. Передача товара между фирмами — продажа одной фирмы и приход у другой.
- **Вход:** один адрес системы. Если человек работает в одной фирме, он попадает сразу в неё. Если в двух — выбирает фирму при входе.
- **Интегратор (суперадмин)** создаёт фирмы, но данные фирмы не видит. Доступ — только по разрешению владельца, на время и с записью в журнал.
- **Уход владельца:** выгрузка всех данных своей фирмы (Excel + полный архив) кнопкой. Это гарантия того, что владелец действительно «владеет».
- **Техника:** spatie/laravel-permission в режиме teams (team = organization) или собственные таблицы ролей той же формы.
- **Подключение второго филиала позже:** создать фирму → пригласить её владельца → он настраивает роли и сотрудников → отдельный импорт из sfon и отдельная параллельная работа. Оценка: 1 день настройки плюс его перенос данных.

### 2.2 Каталог

```
product_types (Смартфон, Планшет, Часы, …)
  └─ families (iPhone, Galaxy S, …)
       └─ models (iPhone 15 Pro, … названия ru/kk/en)
memories, colors, rams (справочники)
variants = модель + память + цвет + ОЗУ   ← «что за телефон»
accessories (артикул, штрихкод, название ru/kk, категория)
```

Справочник общий для обеих фирм (Д1). Цены — у каждой фирмы свои.

### 2.3 Склад: электроника поштучно

**`stock_units`** — один физический телефон:
- фирма, текущий магазин, вариант;
- IMEI 1, IMEI 2, серийный номер;
- состояние: новый / б/у; для б/у — оценка (A/B/C), батарея %, год, описание дефектов, фото;
- статус: `в наличии`, `в резерве`, `в пути` (перемещение), `продан`, `возвращён поставщику`, `списан`;
- себестоимость: сумма, валюта, курс на дату прихода, сумма в ₸;
- цена продажи в ₸;
- поставщик, приход;
- отметка «проверен в госбазе IMEI»: кто и когда (раздел 2.8);
- публичный код для сайта (например `PM-10482`) — не IMEI;
- признак «показывать на сайте».

**Статус и магазин экземпляра меняются только проведением документа**, который одновременно пишет строку в журнал движения.

### 2.4 Склад: аксессуары по количеству

- `accessory_balances` — сколько штук в каком магазине и средняя себестоимость. Это **копия**, пересчитываемая из журнала, руками не меняется.
- Для «новых запечатанных» телефонов тоже поштучный учёт: у них есть IMEI, и продают их по IMEI.

### 2.5 Документы и журналы (сердце системы)

Любая операция — это **документ**: приход, продажа, возврат, перемещение, списание, ревизия, расход, оплата долга, акт trade-in, инкассация.

У документа есть статусы: `черновик` → `проведён` → (при ошибке) `отменён сторно`.

Проведение — одна транзакция базы: либо записалось всё, либо ничего. При проведении пишутся записи в журналы:

| Журнал | Что фиксирует | Что из него считается |
|---|---|---|
| `inventory_movements` | движение товара: экземпляр или аксессуар × кол-во, откуда/куда, себестоимость | остатки, статус и место экземпляра, себестоимость продаж |
| `money_entries` | движение денег по счёту: сумма, валюта, курс, сумма в ₸ | баланс касс и счетов (нал/безнал, ₸/$) |
| `debt_entries` | изменение долга контрагента (клиент или поставщик) | долги клиентов, поставщикам, общий долг |
| `bonus_entries` | начисление и списание бонусов | бонусный баланс клиента |

**Правила журналов:**
- Записи **только добавляются**. Изменение и удаление запрещены триггером в базе — даже владелец и программист через приложение не смогут.
- Ошибка исправляется документом-сторно с обязательной причиной: создаются обратные записи.
- Балансы, остатки и долги — это суммы по журналу. Для скорости хранится готовая копия, она пересчитывается и ночью сверяется с журналом. Если копия не совпала — тревога интегратору.
- Каждая запись ссылается на документ, пользователя, магазин и время.

### 2.6 Продажа

```
sales (документ: магазин, продавец, клиент, источник, доставка, комментарий)
  ├─ sale_lines (экземпляр ИЛИ аксессуар × кол-во, цена, скидка, себестоимость на момент продажи)
  ├─ sale_payments (нал / безнал / Kaspi / в долг / бонусы / зачёт trade-in; сумма; «внесено» и «сдача» для нала)
  └─ tradein_act (если сдал свой телефон в зачёт)
```

Сплит-оплата — несколько строк в `sale_payments`. Сумма оплат обязана равняться сумме чека, иначе документ не проводится.

### 2.7 Защита от двойной продажи одного IMEI

Четыре слоя, каждый ловит то, что пропустил предыдущий:

1. **Уникальный IMEI в фирме.** В базе стоит уникальный индекс на IMEI внутри фирмы. Второй экземпляр с тем же IMEI не завести. Если телефон вернулся (возврат, trade-in) — это **тот же экземпляр**, его история продолжается. Если такой IMEI есть в другой фирме — предупреждение без блокировки.
2. **Резерв при добавлении в корзину.** Экземпляр получает статус «в резерве» за этим продавцом на 30 минут. В другой корзине появится сообщение «уже в корзине у Айдара».
3. **Блокировка строки при проведении.** Продажа берёт экземпляр с `SELECT … FOR UPDATE` и проверяет статус «в наличии / в резерве у меня». Две кассы, нажавшие «оплатить» в одну секунду, выстроятся в очередь: вторая получит ошибку.
4. **Уникальный индекс на активную продажу.** В `sale_lines` стоит частичный уникальный индекс: «экземпляр + продажа не возвращена». Даже при ошибке в коде база не даст записать вторую активную продажу одного телефона.

### 2.8 Курс и валюта в каждой операции

- `exchange_rates`: фирма, курс `$1 = N ₸`, кто и когда установил. Курс ставит админ или владелец вручную.
- Каждая денежная запись и каждая себестоимость хранит: сумму, валюту, **курс на момент операции** и сумму в ₸. Старые операции не пересчитываются при смене курса.
- Покупатель платит только в ₸. В долларах — только закуп, долги поставщикам и аналитика.
- Касса $ — отдельный счёт. Обмен $ → ₸ — документ «конвертация» (две записи по курсу).

### 2.9 Клиенты, персональные данные, госбаза IMEI

- `customers`: имя, телефон (уникален в фирме), согласие на обработку данных (дата, как получено), источник.
- **ИИН** — только у продавцов б/у (акт trade-in). Хранится в шифрованном виде, поиск по «отпечатку». Полностью виден только владельцу и админу, остальным — последние 4 цифры.
- Скан удостоверения не храним (Д: если нужен по закону — отдельное решение, хранение с ограниченным сроком).
- **Госбаза IMEI.** Автоматической проверки нет, поэтому в карточке экземпляра есть отметка «проверен в госбазе: кто, когда, результат». Без отметки касса не даст провести продажу; владелец может отключить это правило в настройках. Автоматическую проверку можно добавить позже, если найдётся официальный сервис.

### 2.10 Trade-in (б/у)

`tradein_acts`: продавец (ФИО, ИИН, телефон, документ — номер), устройство, IMEI, состояние, фото, сумма, способ выплаты (нал или зачёт в покупку), кто принял.

Проведение акта:
- приход экземпляра со статусом «б/у»;
- деньги из кассы или зачёт в продажу;
- печать акта на kk/ru для подписи.

### 2.11 Прочее

- `price_changes` — история цен (кто, когда, было/стало).
- `orders` — заказ покупателя (предоплата, резерв товара, срок).
- `transfers` — перемещение между магазинами одной фирмы: отправил (товар «в пути») → принял в другом магазине (подтверждение) → товар там. Если не приняли — видно, где завис.
- `revisions` — ревизия: сканируем всё, система показывает «лишние», «недостающие», «не в том магазине». Итог — документ корректировки, проводит только владелец или админ.
- `audit_log` — вход, просмотр себестоимости в отчётах, печать, экспорт, изменения настроек, сторно.
- `files` — фото и документы (на диске сервера, превью в WebP).

## 4. Витрина: как получает остатки и цены

### Схема

```
Касса / склад проводит документ
     │  (событие «экземпляр изменился», «цена изменилась», «фото добавлено»)
     ▼
Очередь Redis → задача «обновить карточку витрины»
     ▼
storefront_listings  ← публичная таблица, только безопасные поля
     ▼
Сайт (свой домен, свой пул PHP) читает только её + кэш страниц
```

- Обновление после продажи или смены цены — **обычно до 1 минуты** (оценка).
- Каждую ночь публичная таблица пересобирается целиком из склада и сверяется. Расхождения → в журнал и интегратору.
- Кэш: список каталога и карточки — 60 секунд плюс сброс при изменении. Картинки — отдельные готовые файлы WebP, отдаёт Nginx напрямую.

### Что публично

Модель, память, цвет, ОЗУ, новый/б/у, оценка и батарея (для б/у), год, описание, фото, цена в ₸, магазин (адрес, карта, WhatsApp), публичный код `PM-xxxxx`, статус «в наличии / забронирован».

### Что НЕ публично никогда

IMEI, серийный номер, себестоимость, поставщик, курс закупа, клиенты, долги, продавцы, остатки аксессуаров в штуках (показываем «в наличии» / «под заказ»).

Публичная таблица физически не содержит этих полей, поэтому даже ошибка в шаблоне сайта их не покажет.

### Карточка и WhatsApp

- Каждый телефон — своя страница `/phone/PM-10482` (ваш выбор). Для новых — фото модели (Д5).
- Кнопка «Написать в WhatsApp»: ссылка `wa.me/<номер магазина>` с готовым текстом «Здравствуйте! Интересует iPhone 15 Pro 256 ГБ, PM-10482, 489 000 ₸ — ссылка». Номер берётся из магазина, где лежит телефон.
- Проданный телефон: страница не исчезает, а показывает «Продан» и похожие варианты (ссылки в WhatsApp у клиентов не ломаются). Через 30 дней — убирается из поиска Google.
- Языки: русский и казахский. Разметка товара для Google (Product / Offer), карта сайта.
- Флаг «не показывать на сайте» у экземпляра и у магазина.
- Сайт без входа и без форм с персональными данными. Есть защита от частых запросов.

Премиальный дизайн делаем отдельным этапом, по образцу работы с лендингами (2–3 концепции на выбор).

## 5. Перенос из sfon по шагам

### Главный принцип

Два слоя данных:

1. **Входящие остатки на дату переезда (день X)** попадают в живые журналы:
   - каждый телефон с IMEI и себестоимостью;
   - аксессуары: количество и себестоимость;
   - долги клиентов и поставщикам;
   - балансы касс;
   - бонусы.

   С этого момента все цифры считаются по-новому.
2. **История до дня X** (продажи, приходы, возвраты, клиенты) — в **архив sfon** (отдельные таблицы, только чтение). Её видно в карточке клиента, в поиске по IMEI (гарантия, «кому продавали»), в отчётах «за прошлые периоды».

   В живые журналы история **не проигрывается**: данные sfon неполные (например, нет себестоимости в API), и проигрывание дало бы неверные балансы.

### Откуда что берём

| Данные | API | Excel | Вручную со сверкой |
|---|---|---|---|
| Справочник моделей, память, цвет, ОЗУ | ✔ | | доправить названия на казахском |
| Магазины, контакты, текст гарантии | ✔ | | |
| Товары в наличии: модель, цена, фото б/у, батарея, год | ✔ | | |
| IMEI | — | если экран склада даёт | **скан в день X** |
| Себестоимость | — | если есть в выгрузке приходов/склада | владелец по списку |
| Поставщики | — | история приёмки | |
| Клиенты | — | если экран даёт | из истории продаж |
| Долги клиентов и поставщикам | — | если экран даёт | **владелец подписывает список** |
| Баланс касс | — | | пересчёт денег в день X |
| Бонусы клиентов | — | если экран даёт | |
| История продаж, приходов, возвратов | — | экраны с Excel | **письменный запрос в sfon** |

Для «всей истории» Excel-экранов почти наверняка не хватит. Поэтому шаг 1 — письменный запрос Кайрата в sfon: «прошу выгрузить все данные моей компании (продажи, приходы, клиенты, долги, IMEI) в машиночитаемом виде». Это его данные. Что не удастся получить ни через API, ни через Excel, ни по запросу — сохраняем как PDF/скриншоты в архив, и в документе переноса честно пишем «не перенесено».

### Шаги

1. **Подготовка (неделя 1).**
   - Кайрат получает ключ API в настройках sfon и передаёт интегратору **не через чат**: интегратор сам вносит его на сервер.
   - Отправляется письмо в sfon на полную выгрузку.
   - Делаются все возможные Excel-выгрузки (список экранов — из раздела 8).
2. **Разведка.** Смотрим колонки и полноту выгрузок, составляем таблицу соответствия «поле sfon → поле наше». Каждому объекту ставим метку `sfon_id`, чтобы потом сверять.
3. **Справочники и магазины** — из API в тестовую систему.
4. **Пробный импорт остатков** в тестовую копию: API + Excel. Отчёт:
   - сколько телефонов без IMEI;
   - сколько без себестоимости;
   - сколько не совпало по модели.
   
   Повторяем, пока отчёт не станет коротким.
5. **Клиенты, долги, бонусы** — импорт, затем список долгов печатается. Кайрат проверяет каждую строку и подписывает.
6. **День X (вечером после закрытия):**
   - финальный импорт остатков;
   - **пересчёт всех телефонов сканером** в модуле ревизии: каждый IMEI находит свой экземпляр;
   - лишние → черновик экземпляра для заполнения;
   - недостающие → список «найти»;
   - пересчёт аксессуаров;
   - пересчёт денег в кассах;
   - акт сверки (остатки в штуках и деньгах, долги, кассы) — подпись Кайрата.
7. **Параллельная работа, минимум 14 дней:**
   - **Дни 1–4:** главная — sfon. Продавцы дублируют каждую операцию в новой системе (обучение).
   - **Дни 5–14:** главная — новая система. Дублирование в sfon, чтобы sfon оставался запасным вариантом.
   - **Ночная сверка** (автоматически, ~03:00): из API sfon берём остатки → сравниваем с нашими:
     - новые — количество по варианту и магазину;
     - б/у — поштучно по `sfon_id`;
     - цены.
     
     Отчёт расхождений утром в Telegram владельцу и интегратору. Ноль расхождений 5 дней подряд — условие для следующего шага.
8. **Архив истории** (отдельный этап, когда придёт полная выгрузка): загрузка в архивные таблицы, проверка итогов по месяцам с отчётами sfon (выручка за месяц должна совпасть).
9. **Отключение sfon.** Только когда:
   - 14+ дней параллельной работы;
   - 5 дней без расхождений;
   - финальная полная выгрузка сохранена в наш бэкап (Excel + ответы API);
   - Кайрат дал согласие письменно.

## 6. Деплой, бэкапы, мониторинг, откат

### Сервер

- VPS в Казахстане (ps.kz или hoster.kz), **4 ядра / 8 ГБ / от 100 ГБ NVMe**, Ubuntu 24.04 LTS. Договор — на Кайрата (Д7).
- Nginx (HTTPS Let's Encrypt, автопродление), PHP-FPM — **два пула**: «касса/ERP» и «витрина», PostgreSQL, Redis, Horizon (очереди), планировщик.
- Домены (пример):
  - `erp.<домен>` — система;
  - `<домен>` — витрина;
  - `staging.<домен>` — тестовая копия на том же сервере с отдельной базой, для обучения и репетиций переноса.
- Порты наружу: только 80 и 443 (и SSH по ключу, на нестандартном порту, с fail2ban). База и Redis наружу закрыты.
- Секреты (ключ sfon, пароли базы, ключи шифрования) — только в `.env` на сервере и в GitHub Secrets. В репозитории и в чате — никогда.

### Автодеплой (GitHub Actions)

1. Пуш в `main` → тесты и проверки кода.
2. Сборка релиза → деплой на staging автоматически.
3. На production — **по кнопке подтверждения** (защищённое окружение GitHub), вне рабочих часов магазина.
4. Деплой без простоя: новый релиз кладётся в новую папку, миграции → переключение ссылки на новую папку → проверка здоровья `/health`.
5. Если проверка не прошла — автоматический возврат ссылки на прошлый релиз. Хранятся 5 последних релизов.
6. Миграции базы — только «совместимые назад» (сначала добавляем, удаляем старое следующим релизом). Тогда откат кода не ломает базу.

### Бэкапы (данные остаются в РК)

- **PostgreSQL:** pgBackRest — полная копия раз в неделю, разностная каждую ночь, **непрерывный архив изменений (WAL)**. Можно восстановить базу на любую минуту, а не только на вчерашнюю ночь. Для денег это важно.
- **Фото и файлы:** restic, каждую ночь.
- **Куда:** второе место **в Казахстане**, у другого провайдера (S3-хранилище или маленький VPS). Копии зашифрованы. Ключ шифрования — у Кайрата в запечатанном виде и у интегратора в менеджере паролей.
- **Хранение:** 30 дневных, 12 месячных копий.
- **Проверка восстановления — каждую неделю автоматически:**
  - последний бэкап разворачивается на staging;
  - проверяется, что журналы сходятся с балансами;
  - проверяется число экземпляров и долги.
  
  Результат приходит в Telegram. Раз в квартал — ручная проверка с интегратором («учебная тревога»).

### Мониторинг и тревоги (в Telegram интегратору, важное — владельцу)

- Сайт и система недоступны (внешняя проверка каждую минуту).
- Не прошёл бэкап или проверка восстановления.
- Мало места на диске, высокая нагрузка, падают очереди.
- Сертификат HTTPS скоро истекает.
- Ночная сверка: копии балансов разошлись с журналом; расхождения с sfon; витрина разошлась со складом.
- Бизнес-сигналы (владельцу):
  - сторно и большие скидки за день;
  - продажи ниже себестоимости;
  - касса не закрыта.

Ошибки приложения пишутся в логи на сервере. Внешние сервисы ошибок (Sentry и т.п.) — только без персональных данных или самостоятельно размещённые в РК.

### Откат

| Что случилось | Что делаем |
|---|---|
| Новый релиз сломал экран | Кнопка «откатить» → прошлый релиз за 1 минуту |
| Миграция испортила данные | Восстановление базы на минуту до деплоя (pgBackRest) на staging → проверка → перенос |
| Сервер умер | Новый VPS + восстановление из бэкапа (оценка: 2–4 часа). Инструкция лежит в репозитории |
| Во время параллельной работы новая система неисправна | Магазин продолжает в sfon, данные дозаводятся после починки |

### Честно про 2 недели

**Реально за 2 недели:**
- система на сервере в РК;
- склад и касса первой фирмы;
- реальные остатки загружены и пересчитаны сканером;
- печать чека, гарантии и этикеток;
- базовые отчёты;
- продавцы обучены на тестовой копии.

Можно начинать параллельную работу с sfon.

**Нереально за 2 недели:**
- отключить sfon — минимум +2 недели параллели по вашему же правилу;
- витрина с премиальным дизайном;
- вся история sfon — зависит от sfon, не от нас;
- вторая фирма;
- бот;
- фискальные интеграции.

**Главный риск сроков** — не программирование, а выгрузки из sfon и время Кайрата и продавцов на сверку.

## 8. Риски и что нужно от Кайрата

### Риски

| Риск | Чем грозит | Что делаем |
|---|---|---|
| sfon не отдаст полную историю, а Excel неполный | «Вся история» будет частичной | Письменный запрос сразу; что не получено — архив PDF/скриншотов; честная пометка «не перенесено» |
| Нет IMEI и себестоимости в API | Пустые поля после импорта | Скан в день X, себестоимость по списку от владельца |
| Двойной ввод утомит продавцов | Ошибки, пропуски, саботаж | Не дольше 14 дней, ночная сверка ловит пропуски, ответственный от магазина |
| Нет интернета в магазине | Касса стоит | Резервный мобильный интернет (роутер с SIM), бумажный журнал на час. Офлайн-кассу не делаем — это сложно и опасно для защиты IMEI |
| Один сервер | Простой при поломке | Бэкапы с проверкой, инструкция восстановления, 2–4 часа на подъём |
| Всё знает один интегратор | Нельзя поддерживать без него | Документация в репозитории, стандартный Laravel, доступы у Кайрата (Д7) |
| Ошибка разделения двух фирм | Владелец видит чужие данные | Два слоя защиты (раздел 2.1), тесты, проверка перед запуском второй фирмы |
| Персональные данные и ИИН | Претензии регулятора | Сервер и бэкапы в РК, шифрование ИИН, согласие клиента, политика конфиденциальности, минимум данных в боте. **Юрист должен проверить тексты согласия и акта trade-in** |
| Принтеры не печатают нужный размер | Нет этикеток в день X | Узнать модели в первые дни, тест на месте до дня X |
| Ключ API sfon истечёт во время параллели | Нет ночной сверки | Узнать срок ключа, продлить заранее |
| Разрастание задач («добавим ещё…») | Срыв сроков | Всё новое — в список следующего этапа, не в текущий |
| Ноутбук на Windows 7 | Нет обновлений безопасности; браузер застыл на Chrome 109 | Tailwind 3.4 + Filament 3, данные только на сервере, ограниченная учётная запись, отключение устройства владельцем. Filament 3 со временем перестанут обновлять — переход на 4 после замены ноутбука |

### Что нужно от Кайрата

1. **Ответственный от магазина** — один человек: отвечает на вопросы, проверяет сверки, собирает замечания продавцов. 30–60 минут в день на этапах 2–3.
2. **Доступы на его имя:**
   - договор VPS в РК;
   - домен;
   - аккаунт GitHub (или организация);
   - хранилище бэкапов.
   
   Интегратору — доступ.
3. **sfon:**
   - ключ Open API (передать интегратору лично, не в чат);
   - письмо в sfon на полную выгрузку данных;
   - список экранов sfon, где есть кнопка Excel, и сами выгрузки: склад, история приёмки, продажи, клиенты, долги, бонусы, расходы — что есть;
   - дата окончания оплаченного периода sfon.
4. **Оборудование — модели и фото этикеток:**
   - сканеры;
   - термопринтер этикеток (размер этикетки, например 58×40);
   - чековый принтер (58 или 80 мм);
   - принтер A4.
5. **Люди и права:** список сотрудников, кто в каком магазине, кто админ, кому показывать себестоимость, лимиты скидок.
6. **Правила:**
   - бонусная программа (процент, срок, на что можно тратить);
   - текст гарантии на kk/ru;
   - формы чека, накладной и акта trade-in (если есть текущие);
   - наценки и правила цен.
7. **Бухгалтер:** какие отчёты нужны, как сейчас сдаётся отчётность, нужна ли ЭСФ и когда; реквизиты ИП/ТОО для документов.
8. **Второй филиал:** согласие его владельца на отдельную фирму в системе, его ответственный, его выгрузки sfon, как делится оплата VPS.
9. **Юрист (разово):** тексты согласия на обработку данных, акт trade-in с ИИН, политика конфиденциальности сайта.
10. **Для витрины:** логотип, фирменные цвета, фото магазина, номер WhatsApp каждого магазина, домен.
