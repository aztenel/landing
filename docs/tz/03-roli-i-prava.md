## 0. Коротко

1. Каждая фирма — отдельный аккаунт владельца. Роли, сотрудники, лимиты и устройства живут **внутри фирмы**. Другую фирму не видно никому, кроме её владельца и сотрудников.
2. Шесть ролей: **Владелец**, **Админ**, **Старший продавец**, **Продавец**, **Бухгалтер** — роли фирмы; **Интегратор** — роль системы, данные фирмы видит только по временному разрешению владельца.
3. Права — галочки из общего списка. Часть прав с **лимитом** в ₸. Всё сверх лимита система не запрещает, а предлагает «Отправить заявку» — владелец отвечает с iPhone за секунды.
4. Себестоимость, поставщик, прибыль и полный ИИН **не уходят на устройство** того, кому они не положены: ни в экран, ни в Excel, ни в PDF, ни в поиск.
5. Вход: телефон + пароль. На компьютере магазина — быстрый вход бейджем или PIN. Владелец, админ и бухгалтер — обязательно с 2FA (код из приложения).
6. Работать можно только с **разрешённых устройств**. Украли ноутбук — владелец за 2 нажатия на iPhone отключает его; все входы с него гаснут в течение 10 секунд.
7. Каждое действие пишется в **журнал действий** без права правки и удаления.

## 1. Понятия

| Понятие | Что это | Таблица (архитектура 2.1) |
|---|---|---|
| Фирма | Аккаунт владельца: Prime Mobile. Позже — второй филиал отдельной фирмой | `organizations` |
| Магазин | Точка продаж фирмы. Сейчас один: ТРЦ «Керуен» | `stores` |
| Пользователь | Человек: телефон, пароль, 2FA. Один человек может работать в нескольких фирмах | `users` |
| Членство | Пользователь в конкретной фирме: роль, магазины, личные лимиты, статус (активен / заблокирован / уволен) | `memberships` |
| Доступ к магазину | Членство × магазин × галочки «Продажи» и «Финансы» (как «Прод» и «Фин» в sfon) | `membership_stores` (новая, Допущение) |
| Роль | Набор прав внутри фирмы | `roles`, `role_permissions` |
| Право | Пункт из общего списка системы (код вида `sale.discount`). Список меняет только разработчик | `permissions` |
| Лимит | Число у права: «скидка до 5 000 ₸ на чек» | поле `limit_value` у `role_permissions` и у членства (личный лимит) |
| Заявка | Запрос на действие сверх лимита. Решает владелец (или админ с правом) | `approval_requests` |
| Устройство | Конкретный браузер на конкретном ноутбуке/iPhone, которому фирма разрешила вход | `devices` (новая, Допущение) |
| Сессия | Вход пользователя с устройства. Может быть заблокирована (экран PIN) или закрыта | `sessions` |
| Журнал действий | Кто, что, когда, с какого устройства | `audit_log` |

**Область действия права.** У каждого права одна из областей:
- **свой магазин** — только магазины, отмеченные в членстве (для продавцов всегда так);
- **вся фирма** — все магазины фирмы;
- **свои записи** — только документы, где пользователь автор (например, «мои продажи за день»).

Сейчас магазин один, поэтому «свой магазин» = «вся фирма». Но проверка области делается с первого дня, чтобы второй магазин подключился без переделки.

## 2. Роли по умолчанию

При создании фирмы ей копируются **пять шаблонов ролей**. Дальше владелец меняет их как хочет (кроме «Владельца»). Архитектура 2.1 говорит о трёх стандартных ролях; Допущение: добавляем ещё два готовых шаблона — «Старший продавец» и «Бухгалтер», чтобы Кайрату не собирать их с нуля. Пока ими никто не назначен, они ни на что не влияют.

| Роль | Кто это у Кайрата | Устройство | Главное |
|---|---|---|---|
| **Владелец** | Кайрат | iPhone 17 Pro Max (PWA), иногда ноутбук | Всё. Решает заявки. Единственный, кто видит прибыль фирмы, управляет сотрудниками и устройствами. Роль нельзя удалить или урезать |
| **Админ** | Ержан (если есть) | ноутбук, iPhone | Магазин целиком: приход с себестоимостью, возвраты, сторно, курс, ревизия, долги поставщикам. Не видит прибыль фирмы и не управляет сотрудниками (по умолчанию) |
| **Старший продавец** | опытный продавец, остаётся в магазине за главного | ноутбук, iPhone 12+ | Всё продавца + выше лимиты, перемещение, возвраты аксессуаров, решает мелкие заявки продавцов, если владелец разрешит |
| **Продавец** | Айдар, Дана | ноутбук магазина, iPhone 12+ | Касса, клиенты, приход без себестоимости, trade-in (приём), фото на сайт (по галочке). Себестоимости не видит |
| **Бухгалтер** | Гульнара (приходящий) | ноутбук | Смотрит деньги, долги, отчёты, выгружает Excel. Ничего не продаёт и не меняет на складе |
| **Интегратор** | разработчик | свой компьютер | Создаёт фирмы и первого владельца, чинит. Данные фирмы — только по временному допуску владельца (раздел 13). Не роль фирмы, в списке сотрудников фирмы не показывается |

Правила ролей:
1. В фирме всегда есть хотя бы один активный Владелец. Последнего владельца нельзя заблокировать, уволить или сменить ему роль.
2. Роль «Владелец» не редактируется: у неё все права без лимитов. Владельцев может быть несколько (Допущение: на случай, если Кайрат добавит жену/брата). Второй владелец добавляется только действующим владельцем с повторным подтверждением 2FA.
3. Одному членству — ровно одна роль. Отличия для конкретного человека — через **личные лимиты** (раздел 5.3), а не через вторую роль.
4. Своя роль создаётся копией любой существующей (раздел 16).

## 3. Матрица прав по действиям

**Обозначения:**
- ✔ — можно;
- **Л** — можно в пределах лимита, сверх лимита — заявка (лимиты по умолчанию в разделе 5);
- **З** — только заявкой (каждый раз нужно разрешение);
- 👁 — только смотреть;
- **М** — только в своём магазине (по членству);
- **С** — только свои записи;
- **Д** — интегратор: только по временному допуску владельца (раздел 13);
- — — нельзя, пункт меню не показывается.

Колонки: **Вл** — Владелец, **Ад** — Админ, **СП** — Старший продавец, **Пр** — Продавец, **Бх** — Бухгалтер, **Ин** — Интегратор.

Код права — для разработчика; по нему строится экран галочек роли (раздел 16). Права, помеченные «(Фин)» или «(Прод)», дополнительно требуют галочки «Финансы» / «Продажи» в доступе к магазину.

### 4.2 Как это работает

1. **Поле не уходит в браузер.** Сервер собирает ответ (страницу Filament, компонент Livewire, PDF, Excel, JSON поиска) уже без закрытых полей. Скрыть кнопкой или CSS — нельзя. Проверка: открыть «Инструменты разработчика» в Chrome у продавца — себестоимости в ответе нет.
2. **Закрытые поля вычеркнуты везде:** таблицы, карточки, паспорт телефона, глобальный поиск, подсказки автодополнения, сортировка (нельзя отсортировать по себестоимости, если её не видишь — иначе порядок выдаёт её), фильтры, графики, Excel, PDF, печать, уведомления, текст заявки.
3. **Вывод «по косвенным»** закрыт: продавец не видит «прибыль после скидки» и «наценку %». В заявке «Продажа ниже себестоимости» продавец видит только «Нужно разрешение владельца: цена ниже допустимой», без суммы убытка.
4. **«Вводит, но не видит»** (Допущение: выключено по умолчанию). Если включено у роли продавца: в приходе есть поле «Себестоимость», после сохранения строки оно показывается как «введено ✓», значение больше не отображается этому пользователю. Исправить может только админ/владелец.
5. **Процент от прибыли.** Если продавцу начисляется % от прибыли, он видит только сумму своего заработка за день («Ваш бонус сегодня: 7 400 ₸»), без разбивки по чекам. Допущение: так продавец не может вычислить себестоимость конкретного телефона.
6. **Просмотр себестоимости в отчётах** пишется в журнал действий (архитектура 2.9: «просмотр себестоимости в отчётах»). Записывается факт открытия отчёта, не каждое поле.

## 5. Лимиты

### 5.1 Список лимитов и значения по умолчанию

| L13 | Выкуп дороже сетки, % | (сумма − цена по сетке) / цена по сетке | ∞ | 10 % | 5 % | 0 % |

### 5.2 Правила лимитов

1. **Пустое поле лимита = ∞** (без ограничения). **0 = всегда заявка.** Галочка права выключена = действия нет вообще (кнопки не видно).
2. **Счётчики за день** обнуляются в 00:00 по часовому поясу фирмы. Допущение: часовой пояс фирмы — настройка, по умолчанию `Asia/Almaty`.
3. **Сторно уменьшает счётчик.** Если продажу со скидкой 4 000 ₸ отменили сторно, у продавца освобождается 4 000 ₸ дневного лимита.
4. **Разрешённая заявка не тратит лимит.** Скидка 15 000 ₸ по разрешению владельца не входит в дневной счётчик продавца.
5. **Лимит проверяется на сервере** в момент проведения, в той же транзакции, что и проведение (раздел 02, 2.2 п. 1). Проверка в браузере — только подсказка.
6. **Подсказка до нарушения.** В окне скидки продавец видит «Ваш лимит: до 5 000 ₸ на чек, осталось сегодня 12 000 ₸». Сам лимит и остаток — это не секрет.
7. **Сумма долга считается общая.** Пример: у клиента Асхата долг 70 000 ₸, Дана продаёт ему чехол в долг на 40 000 ₸ → общий долг станет 110 000 ₸ > 100 000 ₸ → заявка «Долг клиента станет 110 000 ₸ (лимит продавца 100 000 ₸)».
8. **Просроченный долг блокирует новый.** Если у клиента есть просроченный долг, новый долг — только заявкой, независимо от суммы (Допущение).

### 5.3 Личные лимиты

1. У членства можно задать личное значение любого лимита: «Дана — скидка до 10 000 ₸». Личное значение заменяет значение роли (может быть и выше, и ниже).
2. Личный лимит виден в карточке сотрудника с пометкой «личный» и кнопкой «Как у роли».
3. Изменение роли не трогает личные лимиты; при смене роли система спрашивает «Сбросить личные лимиты Даны? (3 шт.)».

### 5.4 Пример

Айдар (продавец) продаёт iPhone 15 Pro 256 за 489 000 ₸:
- скидка 4 000 ₸ (0,8 %) — проходит сразу, остаток дневного лимита 16 000 ₸;
- клиент хочет в долг 150 000 ₸, раньше не покупал → нужна заявка (L4 и L6), Айдар нажимает «Отправить заявку»;
- Кайрат на iPhone видит заявку и нажимает «Разрешить с изменением: долг 100 000 ₸, срок 20.11.2026»;
- Айдар видит «Разрешено: долг до 100 000 ₸», меняет оплату: 389 000 ₸ нал + 100 000 ₸ долг → проводит.

### 6.2 Что видит сотрудник

1. В месте срабатывания лимита вместо ошибки — жёлтый блок: «Скидка 15 000 ₸ больше вашего лимита 5 000 ₸. **Отправить заявку владельцу**».

3. Чек блокируется для изменений (кроме «Отменить заявку»). Продавец может открыть **другую вкладку корзины** и обслуживать следующего клиента.

5. Если «Разрешено с изменением» — плашка показывает новое значение: «Разрешено: скидка 10 000 ₸ (вы просили 15 000 ₸)». Продавец нажимает «Применить».
6. Через 30 минут без ответа — «Заявка истекла. Отправить снова?» (срок как в П9).
7. Продавец **не видит**, кто ещё мог решить заявку и почему отклонили, если владелец не написал причину (тогда: «Отклонено»).

### 6.3 Что видит владелец

**Пуш на iPhone (PWA) и Telegram-сообщение** (дубль, см. П9 шаг 2):
- на заблокированном экране — без денег и себестоимости: «Дана просит разрешение: скидка» (Допущение: пуш на экране блокировки видят посторонние);
- после открытия (Face ID телефона + сессия PWA) — карточка заявки.

**Карточка заявки** (одна на экран, крупные кнопки):

| Блок | Пример |
|---|---|
| Кто, где, когда | Дана · ТРЦ Керуен · 14:32 · ноутбук «Касса Керуен» |
| Что просит | Скидка 15 000 ₸ на iPhone 15 Pro 256 Чёрный (PM-10482) |
| Итог чека | 489 000 → 474 000 ₸ |
| Деньги владельца | Себестоимость 422 300 ₸ · прибыль после скидки 51 700 ₸ (10,9 %) |
| Контекст | Клиент Асхат, 3 покупки на 812 000 ₸, долгов нет · скидки Даны сегодня: 4 000 ₸ |
| Причина | «Постоянный клиент» |
| Кнопки | **Разрешить** · **Отклонить** · «Изменить и разрешить» |

1. «Отклонить» открывает поле причины с готовыми вариантами («Слишком большая скидка», «Позвони мне», «Нет»), причина необязательна.
2. «Изменить и разрешить» — поле с новым значением (сумма скидки / сумма долга / дата) и кнопка «Разрешить».
3. Заявки на сумму больше **порога повторного подтверждения** (Допущение: 300 000 ₸, кроме скидок) требуют PIN/Face ID перед «Разрешить» (раздел 10).
4. Блок «Заявки» на «Статистике» владельца показывает все ожидающие, самые старые сверху, счётчик на иконке.

### 6.4 Тайминги

| Событие | Время | Что происходит |
|---|---|---|
| Пуш владельцу | сразу | PWA-пуш + Telegram |
| Напоминание | через 3 мин без ответа | повторный пуш «Дана ждёт уже 3 минуты» |
| Передача админу | через 5 мин без ответа | заявку видят пользователи с `approval.decide`, у которых хватает лимита (раздел 6.6). Владелец по-прежнему может ответить |
| Истечение | 30 мин | статус «Истекла», действие не разблокировано |
| Срок действия разрешения | 15 мин после ответа | если чек не проведён за 15 мин — разрешение сгорает (Допущение) |

### 6.5 Защита от злоупотреблений

1. **Разрешение привязано к чеку.** Сервер хранит «отпечаток» чека в момент заявки: экземпляры, количества, цены, клиент, способ оплаты. Если при проведении отпечаток другой — разрешение недействительно: «Чек изменился после разрешения. Отправьте заявку снова».
2. **Одно разрешение — одно проведение.** Повторно использовать нельзя.
3. **Не больше 3 ожидающих заявок** от одного сотрудника. Четвёртая: «У вас 3 заявки ждут ответа. Дождитесь или отмените одну».
4. **Нельзя решить свою заявку.** Даже если у админа есть `approval.decide`, свою заявку он не видит в списке решений.
5. Все заявки, ответы, изменения и истечения — в журнале действий и отчёте «Заявки за период» (кто сколько просил, сколько разрешено, итог скидок по продавцам).

### 6.6 Кто кроме владельца решает заявки

1. Право `approval.decide` есть у роли (по умолчанию у Админа; у Старшего продавца — выключено, только для скидок можно включить).
2. Решающий может разрешить, только если сумма укладывается **в его собственный лимит**. Пример: админ (лимит скидки 30 000 ₸) может разрешить продавцу скидку 15 000 ₸, но не 40 000 ₸ — такая заявка ему не показывается.
3. Заявки типов «Продажа ниже себестоимости», «Допуск интегратора», «Вход с нового устройства» для ролей «Владелец»/«Админ», «Выгрузка клиентов», «Увольнение» решает **только владелец**.
4. Владелец получает уведомление о каждом решении админа (в ленте, без пуша; Допущение).

## 7. Вход в систему

### 7.1 Способы входа

| Способ | Кто | Где | Как |
|---|---|---|---|
| Телефон + пароль | все | любое разрешённое устройство | основной вход |
| + код 2FA | Владелец, Админ, Бухгалтер (обязательно); остальные — по настройке | | 6 цифр из приложения-аутентификатора (Google Authenticator, «Пароли» iOS) |
| Бейдж + PIN | Продавец, Старший продавец, Админ | только ноутбук, отмеченный как «Компьютер магазина» | скан штрихкода бейджа USB-сканером + PIN 4–6 цифр |
| PIN разблокировки | все | устройство, где уже был полный вход | после автоблокировки (раздел 9) |
| Ключ входа (passkey, Face ID) | Владелец | iPhone | Допущение: этап 3+, вместо пароля и 2FA на своём iPhone. Safari на iOS поддерживает passkeys — проверить на PWA в 1-й день этапа |

### 7.2 Правила пароля и PIN

1. Пароль: не короче 8 символов, не из списка 10 000 самых частых паролей, не совпадает с номером телефона. Требований «заглавная + цифра + символ» нет — они мешают и не помогают.
2. PIN: 4–6 цифр, не `1234`, `0000`, `1111` и не дата рождения из профиля. PIN свой у каждого пользователя на каждое устройство.
3. Хранение: пароль и PIN — только хэш (argon2id или bcrypt), секрет 2FA — зашифрован.
4. Телефон — в формате `+7 7XX XXX XX XX`, уникален среди пользователей системы.

### 7.3 Шаги входа

1. Экран «Вход»: поле «Телефон», поле «Пароль», кнопка «Войти». На ноутбуке магазина сверху — «Отсканируйте бейдж».
2. Сервер проверяет устройство (раздел 8). Неизвестное устройство → раздел 8.2.
3. Если 2FA включена — экран «Код из приложения». Галочка «Запомнить этот iPhone на 30 дней» — только для личного устройства, не для ноутбука магазина.
4. Человек в одной фирме — сразу в неё. В двух — экран выбора фирмы (архитектура 2.1). Переключение фирмы — меню профиля, без повторного пароля, но с новой проверкой прав.
5. Первая страница по роли: Продавец/Старший — «Продажа»; Админ — «Продажа» на ноутбуке, «Склад» на iPhone; Владелец — «Статистика»; Бухгалтер — «Баланс».

### 7.4 Ошибки входа и защита от подбора

| Ситуация | Что видит пользователь | Что делает система |
|---|---|---|
| Неверный телефон или пароль | «Телефон или пароль не подходят» (без уточнения, что именно) | счётчик попыток |
| 5 ошибок подряд по одному телефону | «Слишком много попыток. Попробуйте через 15 минут или попросите владельца сбросить пароль» | блок 15 мин; владельцу уведомление «5 неудачных входов: Дана» |
| 20 ошибок с одного IP за час | то же | блок IP на 1 час, уведомление интегратору |
| Неверный код 2FA 5 раз | «Код не подходит. Проверьте время на телефоне» | блок 15 мин |
| Неверный PIN 5 раз | экран PIN закрывается, нужен полный вход паролем | сессия закрыта |
| Сотрудник заблокирован / уволен | «Доступ закрыт. Обратитесь к владельцу» | запись в журнал |
| Вход в нерабочее время (по настройке, выключено) | «Вход разрешён с 09:00 до 22:00» | Допущение: правило есть, по умолчанию выключено |

### 7.5 Восстановление доступа

1. **Сотрудник забыл пароль** → владелец (или админ с `staff.manage`) нажимает «Сбросить пароль» → система показывает одноразовую ссылку + QR на 24 часа → отправить в WhatsApp. Сотрудник задаёт новый пароль. Старые сессии закрываются.
2. **Сотрудник потерял телефон с 2FA** → владелец «Сбросить 2FA» → при следующем входе сотрудник настраивает 2FA заново.
3. **Владелец потерял iPhone** → вход с ноутбука паролем + **резервный код** (10 одноразовых кодов выдаются при включении 2FA, Кайрат хранит распечатку дома). Если кодов нет — интегратор восстанавливает доступ только после звонка Кайрату и проверки личности при встрече (Допущение: процедура письменная, запись в журнал, всем владельцам фирмы уведомление).
4. SMS-коды на этапе 1 не используем (платные, и SIM можно перевыпустить мошенникам). Допущение.

## 8. Устройства: привязка и отключение

### 8.1 Что такое устройство

1. При первом входе браузер получает случайный **ключ устройства** (длинный, хранится в защищённой cookie на 1 год + копия в `localStorage`). Отпечатков «железа» не собираем.
2. Запись устройства: название («Касса Керуен», «iPhone Даны»), тип (ноутбук / iPhone / другое), магазин (для компьютера магазина), кто разрешил и когда, последний вход, последний IP, браузер и версия, статус: `ожидает` / `разрешено` / `отключено`.
3. Типы устройств:
   - **Компьютер магазина** — привязан к магазину. На нём работают разные люди, есть вход бейджем. Режим «старый ноутбук» — настройка этого устройства.
   - **Личное устройство** — привязано к одному пользователю (iPhone продавца, iPhone владельца). Другой человек с него войти не может без разрешения.
4. Если cookie стёрли (почистили браузер) — устройство считается новым и проходит одобрение заново.

### 8.2 Новое устройство

| Кто входит | Что происходит |
|---|---|
| Продавец, Старший продавец, Бухгалтер | Вход останавливается: «Это новое устройство. Мы отправили запрос владельцу». Владельцу заявка «Дана хочет войти с нового устройства: iPhone, Safari 26, Алматы (по IP)». После «Разрешить» Дана входит без повторного пароля в течение 30 мин |
| Админ | То же, решает только владелец |
| Владелец | Вход с паролем + 2FA разрешается сразу, остальным владельцам и в Telegram — уведомление «Вход владельца с нового устройства» |
| Приглашённый сотрудник по ссылке приглашения | Устройство, где он принял приглашение, разрешается автоматически (владелец сам отправил ссылку) |

Допущение: лимит — не больше 3 разрешённых личных устройств на сотрудника. Компьютеры магазина не ограничены.

### 8.3 Отключение устройства (украли ноутбук)

**Шаги для владельца на iPhone:**
1. «Ещё» → «Устройства».
2. Найти «Касса Керуен» (видно: последний вход 14:32, Дана).
3. «Отключить» → подтверждение Face ID / PIN.
4. Готово: «Устройство отключено. Все входы с него закрыты».

**Что делает система:**
1. Статус устройства → `отключено`, ключ устройства больше не принимается.
2. Все сессии с этого устройства закрываются. Любой следующий запрос с него получает экран «Устройство отключено владельцем». Livewire-опрос на кассе делается раз в 10 секунд — значит, касса гаснет не позже чем через 10 секунд.
3. Бейджи, которыми входили на этом устройстве, продолжают работать на других компьютерах магазина (бейдж не скомпрометирован, если не украден вместе с ноутбуком).
4. Открытые корзины на этом устройстве освобождают резервы через 30 минут, как обычно.
5. Запись в журнал действий и уведомление админу.
6. Кнопка рядом: «Отключить и закрыть все сессии пользователей, работавших на нём сегодня» — на случай, если пароль могли подсмотреть. После этого этим людям нужен полный вход заново.

**На ноутбуке ничего не хранится** (архитектура 1а): нет выгрузок по умолчанию, кэш страниц с данными не сохраняется (заголовки `no-store` для страниц ERP), Excel скачивается только по кнопке и только у ролей с правом экспорта. Допущение: на компьютере магазина экспорт в Excel выключен для всех, кроме владельца (настройка устройства «Разрешить скачивание файлов»).

### 8.4 Другие действия с устройствами

| Действие | Кто | Результат |
|---|---|---|
| Переименовать | Владелец, Админ | «Ноутбук 1» → «Касса Керуен» |
| «Выйти везде» для пользователя | Владелец; сам пользователь — для себя | все сессии пользователя закрыты, устройства остаются разрешёнными |
| Удалить из списка | Владелец | только отключённые; запись в журнале остаётся |
| Ограничение по сети | Владелец | Допущение: выключено. Можно разрешить компьютеру магазина вход только с IP магазина. Не включаем по умолчанию: при резервном мобильном интернете IP меняется |

## 9. Автоблокировка и автовыход

**Блокировка** — экран закрывается, сессия жива, корзина и черновики сохранены. Снять — PIN (или бейдж + PIN на компьютере магазина). **Выход** — сессия закрыта, нужен пароль (и 2FA).

| Роль / устройство | Блокировка после простоя | Полный выход |
|---|---|---|
| Компьютер магазина, любой сотрудник | 10 мин | при закрытии смены; иначе в 03:00 каждую ночь |
| iPhone продавца / старшего продавца | 5 мин | через 12 ч после входа |
| Админ, ноутбук | 15 мин | через 12 ч |
| Админ, iPhone | 5 мин | через 7 дней |
| Бухгалтер | 15 мин | через 12 ч |
| Владелец, iPhone (PWA) | 5 мин (разблокировка PIN или Face ID через passkey) | через 30 дней (с «Запомнить iPhone»), иначе 7 дней |
| Владелец, ноутбук | 15 мин | через 12 ч |
| Интегратор с допуском | — | в конце срока допуска (раздел 13) |

Правила:
1. «Простой» — нет нажатий, ввода, скана и прокрутки. Опрос сервера Livewire простой не прерывает.
2. За 30 секунд до блокировки — плашка «Экран закроется через 30 с. Нажмите любую клавишу».
3. Во время ожидания ответа на заявку блокировка всё равно срабатывает, ответ показывается после разблокировки.
4. **Смена пользователя на кассе:** «Сменить продавца» в шапке → экран бейджа/PIN → корзина предыдущего продавца сохраняется у него, новый продавец видит свою. Продажа подписывается тем, кто вошёл.
5. Таймауты — настройка фирмы (раздел 3.9, `org.security`), не меньше 1 минуты и не больше значений в таблице × 2.

## 10. Повторное подтверждение для опасных действий

Даже при живой сессии система просит PIN (на iPhone — Face ID через passkey, если включён) или пароль + 2FA:

| Действие | Что спрашивает |
|---|---|
| Разрешить заявку на сумму > 300 000 ₸ (кроме скидок) | PIN |
| Смотреть ИИН полностью | PIN, раз в 15 мин |
| Изменить роль, права, лимиты | пароль + 2FA |
| Пригласить / уволить сотрудника | PIN |
| Добавить второго владельца | пароль + 2FA |
| Отключить устройство | PIN |
| Выгрузить клиентов / полный архив фирмы | пароль + 2FA |
| Выключить правило «без госбазы не продаём» | пароль + 2FA + предупреждение о законе ([`00-kazakhstan.md`](00-kazakhstan.md), п. 1) |
| Дать допуск интегратору | пароль + 2FA |
| Изменить реквизиты фирмы, счета, комиссии | PIN |

Подтверждение действует 5 минут для того же типа действия.

## 11. Журнал действий

### 11.1 Что пишется

| Группа | События |
|---|---|
| Вход | успешный вход, неудачная попытка, 2FA, PIN, блокировка, выход, смена фирмы, вход бейджем |
| Устройства | новое устройство, разрешение, отключение, «выйти везде» |
| Документы | создание, проведение, сторно (с причиной), удаление черновика, печать, повторная печать, отправка клиенту |
| Заявки | создание, напоминание, передача админу, решение, изменение, истечение, использование |
| Данные | просмотр отчётов с себестоимостью/прибылью, просмотр полного ИИН, просмотр карточки клиента (Допущение: только у ролей без права выгрузки), экспорт (какой отчёт, период, сколько строк) |
| Цены и сайт | смена цены (было/стало), показ/скрытие, загрузка/удаление фото, порядок, баннеры |
| Настройки | любое изменение настроек фирмы, ролей, прав, лимитов, членств, курса $ |
| Сотрудники | приглашение, принятие, смена роли, личные лимиты, сброс пароля/2FA, блокировка, увольнение, восстановление |
| Интегратор | запрос допуска, решение, каждое действие под допуском, окончание |
| Система | ночная сверка, расхождения, восстановление из копии |

### 11.2 Поля записи

`id`, фирма, время (до миллисекунд), пользователь, роль на тот момент, магазин, устройство (название + ключ), IP, браузер, тип события, объект (тип + id + человекочитаемое название, например «Продажа ПРД-2026-000456»), было / стало (только изменённые поля; себестоимость и ИИН в «было/стало» — маской), причина, id заявки, id запроса (для склейки событий одного действия), хэш (цепочка, как у журналов учёта — [`02-uchet-i-zhurnaly.md`](02-uchet-i-zhurnaly.md), 2.5 п. 5).

### 11.3 Правила

1. Только добавление. Правки и удаления нет ни у кого, включая владельца и интегратора (запрет на уровне базы, как у журналов учёта).
2. Хранение: Допущение — 5 лет в основной базе, затем архив. Записи входа (IP, браузер) — 1 год.
3. Кто видит: таблица 3.9 п. 99. Админ не видит события владельца и интегратора.
4. Экран: лента с фильтрами (сотрудник, период, тип, магазин, устройство, объект) и поиском по номеру документа или IMEI. Из записи — ссылка на документ / паспорт телефона.
5. Экспорт журнала в Excel — только владелец.
6. Карточка сотрудника → вкладка «Действия» = журнал, отфильтрованный по нему (как «по пользователю» в sfon).

## 12. Изоляция фирм

Решение архитектуры 2.1: глобальный фильтр по фирме в приложении + Row Level Security в PostgreSQL. Детализация:

1. **Колонка `organization_id`** — во всех таблицах данных фирмы (документы, журналы, экземпляры, клиенты, деньги, роли, членства, устройства, заявки, журнал действий, файлы, настройки). Исключения — общие таблицы: `users`, `permissions`, справочник моделей (Д1), служебные таблицы системы.
2. **Слой 1 — приложение.** Каждый запрос знает текущую фирму (из сессии после выбора фирмы). Все модели фирмы имеют глобальный фильтр по `organization_id`. Создание записи без фирмы — ошибка.
3. **Слой 2 — база.** На каждую таблицу фирмы включён RLS: строка видна и меняется, только если `organization_id` = значению переменной сессии базы (`app.current_org`). Переменная ставится в начале каждого запроса/задачи и сбрасывается в конце. Приложение подключается к базе **не** владельцем таблиц (иначе RLS обходится).
4. **Фоновые задачи** (очереди, ночная сверка, PDF, витрина) получают `organization_id` в параметрах и ставят переменную сами. Задача без фирмы не запускается.
5. **Файлы** (фото, PDF, Excel) лежат в папках `/<organization_id>/...`, отдаются только через проверку прав или подписанную ссылку на 10 минут. Публичные фото витрины — отдельная копия без данных о фирме-владельце в имени файла.
6. **Кэш, поиск, очереди, уведомления** — ключи с префиксом фирмы.
7. **Номера документов** — свои в каждой фирме (`ПРД-2026-000456` может быть в обеих).
8. **IMEI в другой фирме** — только предупреждение без названия фирмы ([`01-biznes-processy.md`](01-biznes-processy.md), 0.3).
9. **Пользователь в двух фирмах:** членства раздельные, права и лимиты считаются по текущей фирме. Устройства — свои в каждой фирме (владелец второй фирмы разрешает свои). Журнал действий — в каждой фирме свой.
10. **Витрина** — у каждой фирмы своя (свой домен), публичные таблицы витрины тоже с `organization_id`.
11. **Обязательные тесты** перед подключением второй фирмы (архитектура 2.1): для каждой таблицы фирмы и каждого экрана/выгрузки/API — «пользователь фирмы А не видит, не меняет и не находит поиском запись фирмы Б», в том числе подменой id в адресе и в запросе Livewire. Тест на RLS делается прямым SQL под пользователем приложения без фильтра.

## 13. Интегратор и техподдержка

1. **Без допуска** интегратор видит: список фирм, тариф, статус, техметрики, ошибки (с вычищенными персональными данными), журнал своих действий. Не видит ни одной строки данных фирмы.
2. **Запрос допуска:** интегратор в своей панели → фирма → «Запросить доступ» → цель («Не проводится продажа ПРД-2026-000456»), уровень (`только смотреть` / `смотреть и исправлять настройки`), срок (1 ч / 4 ч / 24 ч).
3. Владелец получает заявку (тип «Допуск интегратора») → «Разрешить» с паролем + 2FA → может сократить срок или понизить уровень.
4. Во время допуска:
   - у всех сотрудников фирмы вверху тонкая полоса «Идёт техподдержка до 16:30» (Допущение: чтобы никто не удивлялся изменениям);
   - каждое действие интегратора пишется в журнал с пометкой «техподдержка»;
   - интегратор **не может** проводить документы, делать сторно, менять цены, роли и устройства, видеть полный ИИН. Исправление данных — только через сторно-документ, который проводит владелец или админ (архитектура: журналы только добавлением).
5. Владелец может досрочно «Закрыть доступ» одной кнопкой.
6. **Честное ограничение:** у интегратора как администратора сервера технически есть доступ к базе. Защита: хэш-цепочка журналов (правка сломает цепочку → ночная тревога), шифрование ИИН ключом, которого нет в базе, журнал подключений к серверу, отдельные учётные записи базы. Это записать в договор с Кайратом (Допущение).
7. Создание фирмы: интегратор создаёт фирму, магазин, первого владельца (телефон) → владельцу уходит приглашение (раздел 14). После того как владелец принял приглашение, интегратор теряет право менять сотрудников фирмы.

## 14. Приглашение сотрудника

### 14.1 Поля приглашения

| Поле | Обязательно | Пример | Правило |
|---|---|---|---|
| Имя и фамилия | да | Дана Сейткали | 2–60 символов, печатается в чеке как «Продавец: Дана С.» |
| Телефон | да | +7 701 234 56 78 | формат 7.2; если такой пользователь уже есть в системе — он получает приглашение в эту фирму, свой пароль сохраняет |
| Роль | да | Продавец | из ролей фирмы |
| Магазины | да | ТРЦ Керуен | минимум один; у каждого галочки «Продажи» и «Финансы» (по умолчанию обе) |
| Личные лимиты | нет | скидка до 10 000 ₸ | раздел 5.3 |
| % от прибыли | нет | смартфоны 5 %, аксессуары 10 % | как в sfon; видимость — раздел 4.2 п. 5 |
| Бейдж | нет | «Выдать бейдж» | генерирует код бейджа, PDF для печати 85×54 мм |
| Обязательная 2FA | авто по роли | — | владелец может включить и для продавца |
| Дата начала работы | нет | 10.11.2026 | для отчётов по продавцам |

### 14.2 Шаги

1. Владелец: «Сотрудники» → «Пригласить» → заполняет поля → «Отправить приглашение» (PIN).
2. Система создаёт членство со статусом `приглашён` и одноразовую ссылку на **72 часа**. Показывает три кнопки: «Отправить в WhatsApp» (готовый текст: «Кайрат приглашает вас в Prime Mobile. Откройте ссылку, чтобы задать пароль: …»), «Показать QR» (сотрудник сканирует своим iPhone прямо в магазине), «Скопировать ссылку».
3. Сотрудник открывает ссылку на своём iPhone или на компьютере магазина → видит «Prime Mobile приглашает вас: роль Продавец, магазин ТРЦ Керуен» → галочкой подтверждает «Это мой номер» и задаёт пароль, затем PIN. Допущение: кода из SMS нет (SMS не используем, 7.5 п. 4); защита — ссылка одноразовая, на 72 часа, и владелец видит, где её открыли (14.3).
4. Если роль требует 2FA — экран настройки 2FA с QR-кодом для приложения и 10 резервными кодами.
5. Устройство, на котором принято приглашение, разрешается автоматически (раздел 8.2). На iPhone — подсказка «Добавьте на экран „Домой“» с картинкой, как это сделать в Safari.
6. Первый вход — короткое знакомство из 3 экранов (как сканировать, как отправить заявку, где мои продажи), кнопка «Пропустить».
7. Членство → `активен`. Владельцу уведомление «Дана приняла приглашение».

### 14.3 Исключения

| Ситуация | Что происходит |
|---|---|
| Ссылка истекла | «Приглашение устарело. Попросите владельца отправить новое». У владельца в списке — «Отправить снова» |
| Ссылку открыл не тот человек | Без знания пароля доступ к данным он не получит, но займёт приглашение. Защита: владелец видит «принято с iPhone, Алматы, 14:02» и может «Отозвать доступ» (раздел 15) |
| Пользователь уже работает в другой фирме | Приглашение добавляет вторую фирму; пароль и 2FA прежние; при входе он выберет фирму |
| Тот же телефон уже уволен из этой фирмы | Предложение «Восстановить Дану (уволена 01.09.2026)?» — история продаж та же |
| Владелец отменил приглашение до принятия | Ссылка перестаёт работать |

## 15. Блокировка и увольнение

### 15.1 Блокировка (временно, например подозрение)

1. Владелец: карточка сотрудника → «Заблокировать» → причина (видна только владельцу и админу) → PIN.
2. Сразу: все сессии сотрудника закрыты (≤ 10 с на кассе), бейдж не работает, новые входы — «Доступ закрыт. Обратитесь к владельцу».
3. Ожидающие заявки сотрудника отменяются. Его корзины освобождают резервы. Его черновики остаются (видны админу/владельцу).
4. «Разблокировать» — возвращает доступ без нового приглашения.

### 15.2 Увольнение

**Шаги для владельца** (админ — только заявкой, 3.9 п. 96):
1. Карточка сотрудника → «Уволить».
2. Система показывает **проверки перед увольнением**:
   - открыта ли смена, где он ответственный → «Закройте смену или передайте её другому сотруднику»;
   - деньги под отчётом / незакрытые расходы → сумма;
   - его открытые заказы с предоплатой → «Передать заказы: [выбрать сотрудника]»;
   - заявки с сайта в работе у него → передать;
   - телефоны в резерве за ним → освободятся.
   Ни одна проверка увольнение не запрещает, но владелец подтверждает каждую.
3. Дата увольнения (сегодня по умолчанию; можно завтра — тогда доступ закроется в 00:00), причина (необязательно), PIN.
4. Система: статус членства `уволен`, сессии закрыты, личные устройства сотрудника → `отключено`, бейдж аннулирован, приглашения и сброшенные пароли недействительны, начисления % от прибыли остановлены с этой даты.
5. Если он был единственным, кто знал пароль от компьютера магазина Windows или от Kaspi-кабинета — напоминание владельцу «Смените пароли, которые знал сотрудник» (список ведёт владелец в настройках, Допущение: просто текстовый чек-лист).

**Что остаётся:** пользователь не удаляется. Все его документы, продажи, акты, журнал действий остаются с его именем («Дана С. (уволена)»). В отчётах по продавцам он виден за прошлые периоды.

**Восстановление:** «Восстановить» — членство снова `активен`, роль и магазины прежние (можно поменять), устройства нужно разрешить заново.

### 15.3 Человек в нескольких фирмах

Увольнение из Prime Mobile не трогает его доступ во второй фирме. Блокировку пользователя **во всей системе** (например, мошенник) делает только интегратор по письменной просьбе владельца.

## 16. Управление ролями

### 16.1 Экран «Сотрудники и роли» (макет `erp-4-sotrudniki-i-roli.png`)

1. Слева — список ролей с числом сотрудников. Справа — права выбранной роли, сгруппированные как в разделе 3 (Продажа, Клиенты и долги, Склад, Цены и сайт, Trade-in, Деньги, Документы, Отчёты, Настройки).
2. У каждого права: переключатель, у некоторых — поле лимита с подписью единицы («₸ на чек», «%», «дней»), и одна строка простым языком: «Скидка на чек — сверх лимита продавец отправит заявку вам на телефон».
3. Под группой «Видимость» — переключатели полей из раздела 4.1 (себестоимость, поставщик, прибыль, ИИН полностью, остатки счетов).
4. Кнопка «Сравнить роли» — таблица как раздел 3, только для этой фирмы.

### 16.2 Правила

1. «Создать роль» → «На основе роли: Продавец» → имя → галочки. Пустую роль создать нельзя (нужна основа).
2. Изменения применяются со следующего действия пользователя (права читаются при каждом запросе, кэш сбрасывается при сохранении роли).
3. Нельзя выдать право, которого нет у самого редактирующего (если когда-нибудь админу дадут `role.manage`). Нельзя менять свою роль.
4. Нельзя удалить роль, на которой есть сотрудники: «На роли 2 сотрудника. Сначала переведите их на другую роль».
5. Шаблоны ролей у второй фирмы — свои копии; изменения Кайрата их не трогают (архитектура 2.1).
6. Когда разработчик добавляет новое право в систему, оно по умолчанию **выключено** у всех ролей, кроме «Владельца». Владельцу на «Статистике» — подсказка «Появилась новая возможность: … Включить для ролей?».

## 17. Персональные данные и ИИН

Требования закона — [`00-kazakhstan.md`](00-kazakhstan.md), п. 2 и 3 (пересказы, не проверено юристом).

5. **Сроки хранения** ИИН в актах — Допущение: 5 лет, потом автоматическое обезличивание (уточнить у юриста).
6. Сервер и резервные копии — в РК (архитектура). Внешние сервисы, получающие персональные данные (SMS, WhatsApp-шлюз, Telegram-уведомления), — в уведомлениях **не передаём** ИИН и полный телефон клиента: «Заявка: долг клиенту Асхат •••67».

## 18. Требования к реализации проверок

1. **Права — только на сервере.** Каждое действие Livewire/Filament, каждая ссылка скачивания и каждый endpoint проверяют право через политику Laravel (spatie/laravel-permission + свои политики с лимитами). Скрытая кнопка — только удобство.
2. **Одна функция проверки** вида «может ли пользователь X в фирме Y в магазине Z сделать действие A на сумму S» возвращает: `можно` / `нужна заявка (тип, лимит, текущее значение)` / `нельзя`. Ею пользуются касса, админка, PWA и проведение документа.
3. **Поля** закрываются на уровне подготовки данных (ресурсы/трансформеры), а не в шаблоне. Для каждой модели — список закрытых полей и право, которое их открывает.
4. **Подмена id.** Любой id из запроса (документ, клиент, экземпляр, магазин) проверяется на принадлежность фирме и области права. Тест на каждый ресурс.
5. **Livewire:** закрытые поля не кладутся в публичные свойства компонента (они видны в браузере). Защищённые свойства помечаются как заблокированные от изменения клиентом.
6. **Сессии** — в Redis, с привязкой к устройству. Отключение устройства/пользователя удаляет сессии, а не ждёт их истечения.
7. **HTTPS везде**, cookie `Secure`, `HttpOnly`, `SameSite=Lax`; CSRF-защита Laravel; заголовки `no-store` для страниц ERP.
8. **Ограничение частоты** запросов: вход, PIN, поиск клиентов, экспорт.
9. **Chrome 109 / Safari iOS:** всё перечисленное (cookie, пуши PWA, passkeys) проверяется в обоих браузерах. Пуш-уведомления PWA на iPhone работают только после «Добавить на экран „Домой“» (поэтому дубль в Telegram).
