## 0. Общие правила для всех процессов

### 0.1 Документ, проведение, сторно

1. Любая операция — документ (архитектура 2.5). Статусы: `черновик` → `проведён` → `отменён сторно`.
2. Черновик ничего не меняет в остатках и деньгах. Черновик видит только автор и админ/владелец. Черновик старше 7 дней удаляется сам (Допущение: черновики — не журнал, их удалять можно).
3. Проведение — одна транзакция: все записи в журналы (`inventory_movements`, `money_entries`, `debt_entries`, `bonus_entries`) пишутся вместе или не пишутся совсем.
4. Проведённый документ нельзя изменить или удалить. Ошибку исправляет **сторно**: обратные записи + обязательная причина (не короче 5 символов). Сторно делают админ или владелец (архитектура 3). Продавец может только отправить заявку «отменить».
5. У каждого документа: номер по порядку в фирме в едином формате `<префикс>-<год>-<6 цифр>`: `ПРХ-2026-000123` приход, `ПРД-2026-000456` продажа, `ВЗК-` возврат покупателя, `ТРД-` акт trade-in, `РСХ-` расход, `ДДС-` инкассация и переводы, `ПРМ-` перемещение, `РЕВ-` ревизия, `СПС-` списание, `ОДК-`/`ОДП-` оплата долга, `ЗАК-` заказ, `ГРО-` гарантийное обращение, `СМН-` смена, `ИЗХ-` исправление карточки. Полный список префиксов — раздел 02, п. 2.3 (единственный источник). В тексте ниже номера сокращаются до `ПРД-…`, дата и время, магазин, автор, устройство.

### 0.2 Статусы телефона (экземпляра)

Архитектура 2.3 задаёт основные статусы. Ниже — детализация; добавленные статусы помечены *. **Единый список с кодами и таблица разрешённых переходов — раздел 02, п. 10** (если тексты расходятся, верен 02).

| Статус (код) | Значит | Можно продать | На сайте |
|---|---|---|---|
| `в наличии` (`in_stock`) | лежит в магазине, готов | да | да, если выполнены условия П4.1 |
| `на подготовке`* (`preparing`) | б/у принят, идёт проверка/ремонт/чистка (П6) | нет | нет |
| `в резерве` (`reserved`) | в корзине продавца, 30 мин (П10.1) | только тот, за кем резерв | да, с меткой «Забронирован» |
| `забронирован по заказу`* (`ordered`) | в заказе клиента (П10.2) | только из этого заказа | да, с меткой «Забронирован» |
| `в пути` (`in_transit`) | перемещение отправлено, не принято (П20) | нет | нет |
| `продан` (`sold`) | продан клиенту; в т. ч. принят у клиента по гарантии — флажок «на гарантии у нас» (П13) | нет (только возврат) | страница «Продан» (архитектура 4) |
| `на проверке`* (`on_check`) | вернулся от покупателя, решение не принято (П11) | нет | нет |
| `брак`* (`defective`) | неисправен, ждёт возврата поставщику / ремонта / списания | нет | нет |
| `возвращён поставщику` (`returned_to_supplier`) | отдан поставщику | нет | нет |
| `списан` (`written_off`) | потерян, разбит, разобран на запчасти | нет | нет |

Статус меняется **только** проведением документа (архитектура 2.3). Ручного переключателя статуса нет нигде.

### 0.3 IMEI: ввод и проверки (одинаково во всех процессах)

| Проверка | Правило | Сообщение пользователю |
|---|---|---|
| Длина и символы | IMEI — ровно 15 цифр. Пробелы, дефисы и «/» при скане убираются сами | «IMEI должен быть из 15 цифр. Отсканировано: 14» |
| Контрольная цифра | Алгоритм Луна (15-я цифра) — из [`00-analogi.md`](00-analogi.md), п. 3 | «IMEI с ошибкой: проверьте последнюю цифру. Отсканируйте ещё раз» |
| Не IMEI, а серийник/EAN | Если отсканировано не 15 цифр и это совпадает с форматом штрихкода коробки (EAN-13) — система подсказывает | «Это штрихкод коробки, а не IMEI. Сканируйте строку IMEI на наклейке» |
| Дубль в фирме | Уникальный индекс (архитектура 2.7, слой 1) | «Этот IMEI уже есть: iPhone 15 Pro 256 Чёрный, PM-10482, статус „продан“ 12.10.2026, Дана. Открыть паспорт телефона?» |
| Дубль в другой фирме | Только предупреждение | «IMEI встречается в другой фирме системы. Проверьте телефон» (какая фирма — не показываем) |
| Дубль внутри партии | | «Уже отсканирован в этой партии (строка 4)» |
| IMEI 2 | Для двух-SIM: второй IMEI необязателен, проверяется так же | |
| Техника без IMEI (планшет Wi-Fi, часы, ноутбук) | Вместо IMEI — серийный номер, уникален в фирме, 5–30 символов (буквы/цифры) | |

**Экземпляр выбирается только сканом или вводом IMEI / серийника / публичного кода `PM-xxxxx`**, без выпадающего списка серийников ([`00-analogi.md`](00-analogi.md), п. 4). Поиск по последним 4–6 цифрам IMEI — разрешён, но если нашлось больше одного, система показывает список с моделью, цветом и магазином, и пользователь подтверждает выбор.

**Паспорт телефона** ([`00-analogi.md`](00-analogi.md), п. 1): по скану IMEI в любом месте системы (строка поиска в шапке) открывается карточка с лентой всех событий экземпляра: приход, госбаза, смены цены, фото, публикация на сайте, перемещения, резервы, продажа, возврат, гарантийные обращения, повторный trade-in. Продавец видит ленту без себестоимости и поставщика.

### 0.5 Курс в каждой операции

Каждая сумма в журнале хранит: сумму, валюту, курс на момент операции, сумму в ₸ (архитектура 2.8). Если операция в ₸ — курс всё равно записывается (для аналитики в $). Курс берётся текущий из П2. Задним числом курс не меняется никогда.

### 0.6 Лимиты и заявки

Если действие выходит за лимит роли (скидка, продажа ниже себестоимости, возврат, расход больше лимита, сторно продавцом), система не отказывает, а предлагает «Отправить заявку». Механика — в П9.

### 0.7 Сообщения об ошибках

- Ошибка говорит, **что случилось и что делать**, без кодов: «Телефон уже продан 12.10.2026 (Дана, чек ПРД-2026-000456). Если клиент вернул его — оформите возврат».
- Скан с ошибкой — короткий двойной звук и красная подсветка поля; успешный скан — один «бип» (привычка sfon).
- Ошибка сервера или сети: «Нет связи с сервером. Чек не проведён. Проверьте интернет и нажмите „Оплатить“ ещё раз». Повторное нажатие не создаёт второй чек (защита от двойного проведения: у черновика свой ключ, второй запрос с тем же ключом возвращает уже проведённый документ).

## П1. Открытие смены

**Кто:** продавец (или админ). **Где:** при первом входе в «Продажу» за день — окно «Открыть смену» (ноутбук и iPhone).

**Зачем:** закрепить, кто отвечает за кассу магазина, и сверить наличные на начало дня с тем, что осталось вчера.

### Шаги

1. Продавец входит (телефон + пароль; или бейдж со штрихкодом + PIN, см. вопросы). Попадает сразу в «Продажу».
2. Если смена магазина не открыта — окно «Открыть смену»:
   - система показывает «должно быть в кассе»: остаток кассы ₸ и кассы $ по журналу на конец прошлой смены;
   - продавец пересчитывает и вводит факт: наличные ₸, наличные $;
   - Допущение: ввод по купюрам необязателен (кнопка «по купюрам» открывает таблицу 20 000 / 10 000 / 5 000 / 2 000 / 1 000 / 500 / 200 / 100 ₸ и монеты).
3. Если факт = ожидание — «Смена открыта», документ смены `СМН-…` с временем открытия.
4. Если расхождение — обязательный комментарий, смена открывается, расхождение сразу пишется документом «Расхождение кассы» (раздел 02, п. 8). Больше 1 000 ₸ — уведомление владельцу (не заявка: торговлю не блокируем).
5. Если курс $ сегодня не ставили — после открытия смены окно П2 (только админу/владельцу; продавцу — «Курс сегодня не установлен, используется вчерашний 515 ₸. Сообщите админу»).

### Правила

- В магазине одна открытая смена (не на каждого продавца). Допущение: кассир в магазине общий, деньги одной кассы. Другие продавцы, войдя, работают в открытой смене, но каждая операция подписана своим именем.
- Без открытой смены продажа, возврат, расход из кассы и trade-in за наличные недоступны. Безналичные операции владельца (оплата поставщику с Kaspi Gold) — доступны.
- Расхождение при открытии, как и при закрытии, сразу пишется в денежный журнал (статья «Недостача/излишек кассы»): журнал должен совпадать с деньгами в ящике. Владелец потом решает «Принять» или «Удержать с сотрудника» (П19, шаг 7).

### Пример

Вчера смена закрыта с остатком 184 500 ₸ и $300. Утром Дана насчитала 184 500 ₸ и $300 → смена `СМН-2026-000210` открыта в 10:02. Если бы насчитала 182 500 ₸ — комментарий «не хватает 2 000, разберусь», запись −2 000 ₸ «Недостача кассы», Кайрату уведомление «Открытие смены: −2 000 ₸, Дана» (больше порога 1 000 ₸).

### Журналы

Без расхождения — нет записей в денежном журнале (только документ смены и аудит). С расхождением — одна запись по статье «Недостача/излишек кассы».

## П2. Курс доллара

**Кто:** админ или владелец (архитектура 3). **Где:** шапка системы — «$ 515 ₸» (нажать → окно), на iPhone владельца — плитка на «Статистике».

### Шаги

1. Нажать на курс в шапке → поле «1 $ = ___ ₸», текущий курс и кто его ставил.
2. Ввести новый (до 2 знаков после запятой), «Сохранить».
3. Система записывает `exchange_rates`: фирма, курс, кто, когда. Все следующие операции берут новый курс.

### Проверки

- Курс > 0. Если отличается от прошлого больше чем на 5% — вопрос «Курс изменился на 7,8% (515 → 555). Точно?» (защита от опечатки 5150).
- Старые операции не пересчитываются (архитектура 2.8).
- Розничные цены в ₸ **сами не меняются**. После смены курса предлагается кнопка «Пересчитать розницу по курсу» — только для вариантов, у которых в «Прайсе» цена задана в $ (Допущение: у варианта может быть «цена в $», тогда розница ₸ = цена $ × курс, округление до 1 000 ₸ вверх). Предпросмотр: «Изменится 23 телефона, 12 вариантов». Применение — документ смены цены (П22), сайт обновится сам (П4).

### Исключения

- Курс не ставили сегодня: операции идут по последнему; на главной владельца предупреждение «Курс не обновлялся 2 дня».
- В sfon курс, возможно, пересчитывает цены автоматически — не проверено (см. вопросы).

### Пример

Утром 09.11 Ержан ставит 515 вместо 512. В 12:00 приход 5 iPhone по $820 — себестоимость каждого 820 × 515 = 422 300 ₸. Приход вчера по 512 остаётся по 512.

## П3. Приход электроники по IMEI

**Кто:** владелец, админ; продавец — без себестоимости (архитектура 3, сноска). **Где:** «Склад → Приход → Электроника» на ноутбуке; на iPhone владельца — «Приход» со сканером камерой (макет `iphone-vladelec-2-prihod-skaner.png`).

**Сценарий как в sfon — «буферная партия»:** один раз заполнил, что за телефон и почём, — сканируешь коробки подряд ([`00-sfon-paritet.md`](00-sfon-paritet.md), п. 4.1).

### 3.1 Шапка прихода (заполняется один раз)

| Поле | Обязательно | Правило |
|---|---|---|
| Магазин | да | по умолчанию — магазин пользователя |
| Поставщик | да | выбор из списка; «+ новый поставщик» прямо из формы (имя, телефон, валюта расчётов) |
| Валюта закупа | да | ₸ или $; по умолчанию — валюта поставщика |
| Курс | да, если $ | подставляется действующий (П2). Поменять только для этого прихода (например, курс из договора) может **только владелец**, с причиной (раздел 02, п. 3.3) |
| Номер накладной поставщика | нет | текст |
| Оплата поставщику | да | «Оплачено сразу» (выбрать счёт: касса $, касса ₸, Kaspi Gold…) / «В долг поставщику» / «Частично»: сумма оплаты + остальное в долг |
| Срок оплаты долга | если долг | дата; по умолчанию +14 дней (Допущение) |
| Комментарий | нет | |

### 3.2 Строка партии (группа одинаковых телефонов)

| Поле | Обязательно | Правило |
|---|---|---|
| Тип → семейство → модель | да | поиск одной строкой «15 pro»; справочник пополняется прямо из формы (только админ/владелец) |
| Память, цвет, ОЗУ | да (ОЗУ — если у модели есть варианты) | |
| Состояние | да | Новый / Б/у |
| Цена закупа за штуку | да* | в валюте шапки. *Продавец поле не видит: строка уходит «без себестоимости» и попадает в список «Приходы без себестоимости» админу (архитектура 3) |
| Розничная цена ₸ | да | подставляется из «Прайса» по варианту; можно изменить для партии |
| Гарантия, мес | да | по умолчанию из настроек: новый 12, б/у 1 (шаблоны sfon, [`00-sfon-paritet.md`](00-sfon-paritet.md), п. 5) |
| Для б/у: грейд A/B/C, батарея %, год, дефекты, «заменены детали» | да для б/у (кроме дефектов) | грейды словами: A «Отличное», B «Хорошее», C «Заметные следы» ([`00-analogi.md`](00-analogi.md), п. 6) |
| Ожидаемое количество | нет | если указано — счётчик «7 из 10» |
| Госбаза | нет | галочка «Все проверены в госбазе сейчас» + источник (П5) |
| Показать на сайте | да | по умолчанию включено и у новых, и у б/у. Б/у всё равно не виден, пока у него нет своего фото и пока он `на подготовке` — поэтому первое фото сразу публикует телефон (раздел 05, п. 4) |

### 3.3 Шаги — ноутбук с USB-сканером

1. «Склад → Приход → Новый приход». Заполнить шапку.
2. «+ Партия»: модель, память, цвет, состояние, цена закупа, розница. Курсор встаёт в поле «IMEI».
3. Сканировать IMEI с коробок подряд. После каждого скана: проверки из 0.3 → строка «✔ 356789…1234» и бип. Счётчик «7 из 10».
4. Ошибочный скан не останавливает партию: строка красная с причиной, следующий скан принимается. Красные строки нельзя провести — их нужно удалить или исправить.
5. Если у телефона два IMEI — после первого скана система ждёт второй 2 секунды (Допущение); если второй не пришёл — строка сохраняется с одним IMEI. Можно настроить «Сканировать IMEI 2: всегда / никогда / по ситуации».
6. Следующая модель — «+ Партия». В одном приходе можно смешать несколько моделей и аксессуары (П7) от одного поставщика.
7. Внизу сводка: штук, сумма закупа в валюте и в ₸, ожидаемая розница, расчётная маржа (маржа — только с правом на себестоимость).
8. «Оприходовать» → окно подтверждения «Оприходовать 10 телефонов на $8 200 (4 223 000 ₸)? Долг поставщику ТОО „Мобайл-Трейд“: $8 200, срок 23.11.2026» → «Да».
9. Проведение: экземпляры получают статус `в наличии` (новые) или `на подготовке` (б/у, если включено правило П6), публичные коды `PM-xxxxx`, движение в журнал, деньги/долг в журналы.
10. Предложение «Печать этикеток: 10 шт.» (термоэтикетка: модель, память, цвет, IMEI штрихкодом, `PM-код`, цена; казахский + русский).

### 3.4 Шаги — iPhone владельца, сканер камерой

1. «Приход» → шапка (поставщик, валюта, оплата) — одним экраном, последние значения подставлены.
2. Модель — поиском или **сканом штрихкода коробки** (EAN): если EAN уже привязан к варианту, модель/память/цвет подставляются сами. Если не привязан — выбрать вариант вручную, система запомнит EAN → вариант (Допущение).
3. Экран камеры (макет): рамка, фонарик, «IMEI найден: 35 678912 345678 9 ✔», вибрация. Камера читает штрихкод Code-128 с наклейки коробки; если на коробке несколько штрихкодов — система берёт тот, что проходит проверку IMEI (15 цифр + Луна).
4. После каждого скана — кнопка «📷 Фото» (необязательно): сразу снять телефон для сайта (П4).
5. «Готово» → сводка → «Оприходовать».

### 3.5 Шаги — вручную (наклейка стёрта, сканер не читает)

1. В поле IMEI набрать 15 цифр. На iPhone — цифровая клавиатура.
2. Проверка Луна обязательна; при ручном вводе — поле «повторите IMEI» (двойной ввод, Допущение) или сверка с `*#06#` на включённом телефоне.
3. В паспорте телефона отметка «IMEI введён вручную».

### 3.6 Импорт из Excel (большие поставки)

Шаблон: модель, память, цвет, ОЗУ, состояние, IMEI1, IMEI2, цена закупа, розница. Загрузка → предпросмотр с теми же проверками → проведение одним документом. Источник: [`00-analogi.md`](00-analogi.md), п. 2.

### 3.7 Исключения и ошибки

| Ситуация | Что делает система |
|---|---|
| IMEI уже в фирме и телефон `продан` | Не даёт оприходовать как новый. Подсказка: «Этот телефон продан 12.10 клиенту А. Если он вернулся — оформите возврат (П11) или trade-in (П12)». Тот же экземпляр, история продолжается (архитектура 2.7) |
| IMEI уже в фирме и `в наличии` | «Уже на складе: PM-10482, ТРЦ Керуен» — строка красная |
| Поставщик в $, а курс не ставили 3 дня | Предупреждение перед проведением «Курс 515 от 06.11. Обновить?» |
| Розница ниже закупа | Предупреждение «Розница 410 000 ₸ ниже себестоимости 422 300 ₸» (проводить можно, только с правом себестоимости) |
| Продавец без права себестоимости | Цена закупа скрыта; документ проводится, экземпляры получают пометку «нет себестоимости» и **не могут быть проданы**, пока админ не внесёт себестоимость (Допущение: иначе прибыль в отчёте будет неверной) |
| Сеть пропала посреди партии | Отсканированные IMEI хранятся в черновике на сервере после каждого скана; при обрыве — сохранённое в браузере дописывается при восстановлении связи (Допущение) |
| Ошибся моделью/ценой после проведения | Сторно прихода целиком (если ни один телефон ещё не продан) или документ «Исправление карточки» (`ИЗХ-…`) по экземпляру — П3.9 |
| Часть телефонов из партии уже продана, ошибка в себестоимости | Документ «Корректировка себестоимости» (`КСБ-…`, только владелец) — новая запись в журнале; по уже проданным разница попадает в прибыль **датой корректировки**, прошлые дни не меняются (раздел 02, операция № 49) |

### 3.8 Примеры

**А. Новые в долг в $.** Поставщик «Мобайл-Трейд», 10 × iPhone 15 Pro 256 Natural, $820 за штуку, курс 515, в долг, срок 14 дней. Розница 489 000 ₸.
- Себестоимость: $820 × 515 = 422 300 ₸ за штуку, всего $8 200 = 4 223 000 ₸.
- Ожидаемая розница: 4 890 000 ₸, маржа 667 000 ₸ (13,6%).
- Журналы: 10 записей прихода в `inventory_movements`; `debt_entries`: долг поставщику +$8 200 (курс 515, 4 223 000 ₸).

**Б. Частично оплачено в ₸.** 5 × Samsung A55 8/256, 165 000 ₸ закуп, итого 825 000 ₸. Оплачено 500 000 ₸ с Kaspi Gold, 325 000 ₸ в долг. Журналы: `money_entries` Kaspi Gold −500 000 ₸; `debt_entries` поставщику +325 000 ₸.

**В. Б/у от поставщика.** 1 × iPhone 13 128 Midnight, б/у, грейд B, батарея 84%, закуп 155 000 ₸, розница 199 000 ₸ → статус `на подготовке` (П6).

### 3.9 Исправление карточки телефона (пересорт, опечатка IMEI)

Добавлено при сверке разделов: в sfon есть «изменение цвета/памяти/ОЗУ» в истории товара ([`00-sfon-paritet.md`](00-sfon-paritet.md), п. 4.10), а у нас статус и данные экземпляра меняются только документом.

**Кто:** админ, владелец (право `stock.unit_edit`, раздел 03); продавец — заявкой. **Где:** паспорт телефона → «Исправить карточку» (Э10.3).

1. Что можно исправить: модель, память, цвет, ОЗУ, новый/б/у, грейд, батарея, год, IMEI 1 / IMEI 2 / серийный (только опечатка).
2. Обязательны причина (список: «ошибка при приходе», «пересорт у поставщика», «опечатка IMEI», «другое» + текст) и подтверждение «было → стало» на одном экране.
3. Новый IMEI проходит все проверки 0.3 (Луна, дубль в фирме). После смены IMEI отметка госбазы сбрасывается — нужна новая проверка (П5).
4. Проведение — документ `ИЗХ-…`: журнал товара не пишется (это не движение), запись «было → стало» видна в ленте паспорта и в журнале действий. Если сменился вариант — цена берётся из «Прайса» нового варианта (с предпросмотром), сайт обновляется сам (П4).
5. Ограничения: у проданного телефона можно исправить только опечатку IMEI (админ/владелец, с причиной); модель/память у проданного не меняются — это возврат и новая продажа.

**Пример.** В приходе 10 × iPhone 15 Pro 256 Natural один оказался Blue. Ержан открывает `PM-10489` → «Исправить карточку» → цвет Natural → Blue, причина «пересорт у поставщика» → `ИЗХ-2026-000003`. Цена та же (489 000 ₸), на сайте карточка переехала в Blue за ≤ 60 с.

## П4. Публикация на сайте: фото, цена, показать/скрыть, порядок

**Главное требование владельца:** Кайрат фотографирует телефон в админке с iPhone → телефон сразу появляется на сайте. Никакой отдельной «админки сайта»: сайт — это вид того же склада (архитектура 4, `storefront_listings`).

**Кто:** владелец, админ; продавец — добавить фото (Допущение: продавец может снимать фото, но включать показ и менять цену — нет). **Где:** iPhone — паспорт телефона (скан IMEI или `PM-код`) → вкладка «Сайт»; ноутбук — «Склад → Телефоны → карточка → Сайт» и «Склад → Сайт» (список всего, что показано).

### 4.1 Когда телефон виден на сайте (все условия сразу)

1. Статус `в наличии`, `в резерве` или `забронирован по заказу` (последние два — с меткой «Забронирован»).
2. Галочка «Показывать на сайте» у экземпляра включена.
3. Магазин не скрыт с сайта; модель/бренд/категория не скрыты (видимость на уровнях категории, бренда, модели, экземпляра, магазина — как в sfon, [`00-sfon-paritet.md`](00-sfon-paritet.md), п. 8).
4. Розничная цена > 0.
5. Есть фото: у нового — фото модели из справочника подходит (архитектура Д5); у б/у — минимум 1 своё фото (Допущение: рекомендуем 4: перед, зад, бока, экран включён; при < 3 — подсказка «Добавьте фото, с ними продают быстрее»).
6. Себестоимость внесена (Допущение: не показываем то, что нельзя продать, см. П3.7).

Если условие не выполнено, во вкладке «Сайт» написано, какое именно: «Не на сайте: нет фото» — кнопкой сразу исправить.

### 4.2 Шаги «сфотографировал — появился»

1. Владелец на iPhone: строка поиска → скан IMEI камерой (или ввод `PM-10482`) → паспорт телефона.
2. «Сайт» → «📷 Добавить фото» → камера iPhone (несколько снимков подряд) или выбор из галереи.
3. Фото загружаются сразу; на сервере: уменьшение, WebP, превью, удаление геоданных из файла. Индикатор «Загружено 4 из 4».
4. Порядок фото — перетаскиванием; первое — главное. Удалить фото — свайп/корзина (фото уходит из сайта, сам файл хранится 30 дней, Допущение).
5. Переключатель «Показывать на сайте» уже включён по умолчанию (П3.2) — отдельно включать не нужно. Выключают его, только чтобы скрыть телефон.
6. Через ≤ 1 минуту (обычно секунды; оценка из архитектуры 4) телефон на сайте. Кнопка «Открыть на сайте» ведёт на `/phone/PM-10482`.

### 4.3 Что ещё меняется из той же вкладки

| Действие | Кто | Как | Что на сайте |
|---|---|---|---|
| Цена | владелец, админ | поле «Цена ₸» → «Сохранить» → это документ смены цены (П22) с историей было/стало | новая цена ≤ 1 мин |
| Старая цена (зачёркнутая) | владелец | поле «Цена до скидки» (необязательно) | показывается зачёркнутой |
| Скрыть / показать | владелец, админ | переключатель | исчезает / появляется ≤ 1 мин |
| Порядок в каталоге | владелец | «Поднять наверх» (закрепить в начале своей категории) / «Обычный порядок»; на ноутбуке — список «Склад → Сайт» с перетаскиванием | порядок в списке |
| Описание | владелец, админ | текст ru и kk (для б/у — что с телефоном) | в карточке |
| «Хит», «Новинка», «Скидка» | владелец | метки | значок на карточке |

### 4.4 Правила синхронизации (обязательны)

- Продажа, резерв, возврат, перемещение, смена цены, фото — каждое событие обновляет сайт само. Ручной кнопки «выгрузить на сайт» нет.
- На сайт никогда не уходят IMEI, серийник, себестоимость, поставщик, клиенты (архитектура 4).
- Новые одинаковые телефоны в каталоге свёрнуты: «iPhone 15 Pro 256 Natural — 489 000 ₸, в наличии 7» (Д5); б/у — каждый отдельной карточкой.
- Проданный — страница «Продан» + похожие (архитектура 4).
- Значок «Проверен в госбазе IMEI» на карточке, если отметка есть (без самого IMEI, [`00-kazakhstan.md`](00-kazakhstan.md), п. 1).
- Для б/у на сайте: грейд словами, батарея %; при батарее < 80% — пометка «нужна замена батареи» (Допущение из [`00-analogi.md`](00-analogi.md), п. 6); «заменены детали: …» если отмечено.

### 4.5 Пример

13:40 Кайрат принял iPhone 13 128 по trade-in, П6 закончена в 16:10 (батарея заменена). В 16:12 он сканирует IMEI, снимает 4 фото, ставит цену 219 000 ₸, включает показ. В 16:13 на сайте карточка `PM-10517`, грейд B «Хорошее», батарея 100% («заменена батарея»). В 18:05 Айдар продаёт его — в 18:06 на сайте «Продан».

## П5. Проверка в госбазе IMEI

**Почему обязательно:** по закону № 320-VIII от 19.06.2026 продавец должен проверить IMEI до продажи, указать IMEI в документах и сообщить покупателю (по пересказам, не проверено по тексту закона — [`00-kazakhstan.md`](00-kazakhstan.md), п. 1). Автоматической проверки нет, поэтому — ручная отметка (архитектура 2.9).

**Кто:** любой сотрудник. **Где:** паспорт телефона → «Госбаза»; при приходе — галочка на партию; в кассе — окно, если отметки нет.

### Поля отметки

| Поле | Значения |
|---|---|
| Результат | Верифицирован / Не верифицирован / Заблокирован (в розыске, ограничения) |
| Источник | imei.rfs.gov.kz / eGov Mobile / Kaspi / другое (адрес официальной проверки уточнить — не проверено) |
| Кто, когда | автоматически |
| Подтверждение | необязательно: скриншот результата (фото с iPhone) |

### Шаги

1. Кнопка «Проверить в госбазе» открывает сайт проверки в новой вкладке и копирует первые 14 цифр IMEI в буфер ([`00-kazakhstan.md`](00-kazakhstan.md)).
2. Сотрудник вставляет, смотрит результат, возвращается и нажимает результат.
3. Для партии новых: галочка «Все проверены» ставит отметку всем экземплярам партии одной записью (Допущение: допустимо для новых от постоянного поставщика; для б/у — только по одному).

### Правила в кассе

- Продажа телефона без отметки «Верифицирован» **блокируется** (архитектура 2.9).
- Отметка старше 7 дней (настройка, Допущение) — касса просит проверить снова: окно прямо в кассе, продажа продолжается после отметки.
- «Не верифицирован» / «Заблокирован» → экземпляр нельзя продать и он скрывается с сайта; уведомление владельцу; дальше — возврат поставщику (П15) или решение владельца.
- Выключатель «Продавать без проверки» — только владелец, с предупреждением о законе; каждая такая продажа в журнале и отчёте «Продано без проверки госбазы».
- IMEI печатается в чеке, гарантийном талоне и (когда будет интеграция) в строке фискального чека.

### Пример

Айдар сканирует iPhone 15 Pro, PM-10482, отметка от 25.10 (15 дней назад) → окно «Проверка госбазы устарела. Проверьте сейчас» → кнопка, сайт открылся, «Верифицирован» → продажа продолжилась. Время: ~30 секунд.

## П6. Подготовка б/у к продаже

**Источник:** [`00-analogi.md`](00-analogi.md), п. 7. **Кто:** админ, владелец (продавец — добавляет работы и фото). **Где:** «Склад → На подготовке» (список) и паспорт телефона.

### Шаги

1. Б/у телефон после прихода или trade-in получает статус `на подготовке` (Допущение: настройка «Б/у сначала на подготовку» включена; если выключена — сразу `в наличии`).
2. В паспорте — чек-лист подготовки: сброс до заводских, iCloud/Google отвязан (повторно), чистка, проверка, плёнка; каждая галочка с именем и временем.
3. Работы и запчасти — кнопка «+ Затрата»: что (замена батареи, экрана, корпус, ремонт у партнёра), сумма, валюта, оплачено откуда (касса / счёт / в долг мастеру-поставщику). Затрата **добавляется к себестоимости** экземпляра (запись в журнал движения как «доп. себестоимость»; деньги — в денежный журнал или долг).
4. Обновить грейд, батарею, «заменены детали», описание.
5. Фото и цена (П4). Подсказка цены: «За 90 дней такие (iPhone 13 128, B) выкупали в среднем за 148 000 ₸, продавали за 212 000 ₸ за 9 дней» ([`00-analogi.md`](00-analogi.md), п. 8).
6. «Готов к продаже» → документ `Ввод в продажу`: статус `в наличии`, на сайте — если включён показ.

### Проверки

- Нельзя «Готов к продаже» без розничной цены, без отметки госбазы «Верифицирован» и без галочки «iCloud/FRP отвязан».
- Затрата после продажи телефона — нельзя (только расход по статье П17).

### Пример

Выкуп iPhone 13 128 — 150 000 ₸. Батарея у мастера 18 000 ₸ (наличными из кассы). Себестоимость 168 000 ₸. Цена 219 000 ₸ → ожидаемая прибыль 51 000 ₸. В отчёте «Отчёт по б/у»: выкуп 150 000, подготовка 18 000, срок подготовки 1 день.

## П7. Приход аксессуаров

**Кто:** админ, владелец; продавец — без себестоимости. **Где:** «Склад → Приход → Аксессуары» (тот же документ, что П3, вкладка; один приход может содержать телефоны и аксессуары).

### Шаги

1. Шапка — как в П3.1.
2. Добавление позиции:
   - **сканом штрихкода** (EAN) — если товар есть в справочнике, он добавляется с количеством 1; каждый следующий скан того же штрихкода +1;
   - если штрихкода нет в справочнике — окно «Новый товар»: название ru, название kk (необязательно сейчас, но без него ценник не печатается — [`00-kazakhstan.md`](00-kazakhstan.md), п. 9), категория, бренд, совместимость (модели), штрихкод, артикул; сохраняется в справочник;
   - **поиском** по названию/артикулу + ввод количества.
3. По каждой строке: количество, цена закупа за шт. (валюта шапки), розница ₸ (из «Прайса»; можно изменить — это смена цены всего товара, П22).
4. Сводка, «Оприходовать».
5. Проведение: `inventory_movements` +кол-во; средняя себестоимость пересчитывается: (старый остаток × старая ср. себестоимость + новое кол-во × новая цена в ₸) / общий остаток.
6. Печать ценников / стикеров (полочный ценник или стикер на упаковку, kk + ru).

### Исключения

| Ситуация | Правило |
|---|---|
| Товар без штрихкода | система создаёт свой внутренний штрихкод (Допущение: `2xxxxxxxxxxxx`, EAN-13 внутреннего диапазона) и печатает стикер |
| Один штрихкод у двух разных товаров | при скане — выбор из двух; админу задача «развести штрихкоды» |
| Нет казахского названия | приход проводится, товар попадает в список «Нет перевода», ценник не печатается |
| Ошибка в количестве после проведения | сторно строки/документа, если остаток позволяет; иначе — корректировка через ревизию (П21) |

### Пример

Поставщик «Аксессуар-Опт», в ₸: 50 × чехол iPhone 15 Pro силикон по 1 200 ₸, 30 × стекло по 400 ₸, 20 × зарядка 20W по 2 900 ₸. Итого 60 000 + 12 000 + 58 000 = 130 000 ₸, оплачено наличными из кассы. Розница 4 990 / 2 990 / 7 990 ₸. На складе было 10 чехлов по 1 100 ₸ → новая средняя (10×1 100 + 50×1 200)/60 = 1 183,33 ₸.

## П8. Продажа

**Кто:** продавец, админ, владелец. **Где:** «Продажа» — ноутбук (макет `erp-2-prodazha.png`) и iPhone продавца (макеты `iphone-prodavec-1-pustoi-chek.png`, `iphone-prodavec-2-chek.png`). Одна корзина для телефонов и аксессуаров (в sfon — две кассы; [`00-sfon-paritet.md`](00-sfon-paritet.md), п. 6.1). Переключатель «Электроника / Аксессуары» оставлен только как фильтр в «Товарах» (привычка).

### 8.1 Шаги

1. **Скан.** Поле скана всегда в фокусе (F2). Скан IMEI, `PM-кода` или штрихкода аксессуара. На iPhone — кнопка камеры.
2. **Автодобавление** через 0,8 с после последнего символа (настройка; выключено → Enter). Бип.
3. **Резерв.** Телефон, попавший в корзину, получает статус `в резерве` за продавцом на 30 мин (архитектура 2.7, слой 2). Таймер в строке. На сайте — «Забронирован».
4. **Корзина:** фото, модель, память, цвет, IMEI (последние 6 цифр), гарантия, цена; аксессуар — кол-во «− 1 +». Поиск товара без скана — «Товары» (каталог с наличием по всем магазинам, без себестоимости).
5. **Клиент** (F4 поиск, F3 новый: имя, телефон +7, галочка согласия на обработку данных — обязательна при сохранении). Клиент обязателен для: долга, списания и начисления бонусов, доставки. Для гарантии — желателен (Допущение: без клиента гарантия действует по чеку). Для безнала — **не** обязателен (Допущение, отличие от sfon).
6. **Бонусы** (если клиент выбран): «Доступно 12 400 ₸ бонусов» → «Списать» (сумма ≤ доступного и ≤ 20% чека, Допущение). Подтверждение кодом в SMS/WhatsApp — настройка (по умолчанию выключено, Допущение).
7. **Скидка:** на строку или на чек, в ₸ или %. Лимит роли (например, продавец — до 5 000 ₸ на чек; архитектура 3). Сверх лимита — кнопка «Запросить у владельца» (П9), чек ждёт ответа, продавец может обслуживать другого клиента в другой вкладке корзины.
8. **Trade-in (F8)** — если клиент сдаёт телефон в зачёт: П12, сумма зачёта встаёт строкой оплаты «Trade-in».
9. **Доставка** (необязательно): адрес, стоимость, кто платит (клиент в чеке / курьеру наличными / за счёт магазина — расход), служба или курьер, статус (собран → у курьера → доставлен).
10. **Источник** (Instagram, 2ГИС, сайт, рекомендация, проходил мимо, Kaspi…) — список из настроек; по умолчанию берётся из карточки клиента. **Комментарий** — текст.
11. **Оплата (F9)** — окно оплаты (8.2).
12. **Проведение** (8.3) → печать (8.4).

### 8.2 Окно оплаты

| Способ | Что вводится | Куда деньги |
|---|---|---|
| Наличные ₸ | «Внесено» (кнопки купюр 5 000 / 10 000 / 20 000 / «без сдачи»), сдача считается сама | касса ₸ магазина |
| Наличные $ | Допущение: **запрещено** — покупатель платит только в ₸ (архитектура 2.8). Если клиент принёс $ — сначала «Обмен валюты» (П18) | — |
| Kaspi QR / Kaspi перевод (Gold) | сумма; номер операции — необязательно | счёт «Kaspi QR» / «Kaspi Gold» |
| Карта (терминал) | сумма; счёт терминала | счёт «Терминал …» |
| Рассрочка банка (Kaspi Red/Kredit/рассрочка, Halyk, Home Credit, Freedom) | сумма, банк, срок (3/6/12/24 мес), номер договора/заявки | счёт рассрочки банка; комиссия — отдельная запись |
| В долг | сумма, дата возврата (обязательна), клиент обязателен | долг клиента (П14) |
| Бонусы | из шага 6 | списание бонусов |
| Trade-in | из шага 8 | зачёт (П12) |
| Предоплата по заказу | подставляется сама, если продажа из заказа (П10) | закрывает аванс клиента |

**Правила окна:**
- Любая комбинация — сплит (несколько строк).
- «Свести под расчёт» — последняя строка оплаты автоматически = остаток.
- Пока сумма оплат ≠ сумме чека — надпись «Баланс не сведён: не хватает 39 000 ₸» и кнопка «Провести» неактивна (архитектура 2.6).
- Сдача только с наличных ₸; «Внесено» не может быть меньше суммы наличными.
- Комиссия банка: у каждого счёта процент по умолчанию (настройка фирмы; для Kaspi рассрочки — 12–15%, не проверено, задаёт Кайрат). Допущение: продавец комиссию не видит, она считается при проведении и видна владельцу в прибыли чека.
- Рассрочка банка — **не долг клиента** ([`00-kazakhstan.md`](00-kazakhstan.md), п. 6).
- Поле «Номер фискального чека» — необязательно на этапе 1 (чек пробивается в приложении кассы отдельно), продажи без номера — в отчёт «Продажи без фискального чека» ([`00-kazakhstan.md`](00-kazakhstan.md), п. 4).

### 8.3 Проверки при проведении (в одной транзакции)

1. Для каждого телефона: блокировка строки, статус `в резерве` у этого продавца или `в наличии` (архитектура 2.7, слой 3).
2. Отметка госбазы «Верифицирован» и не старше 7 дней (П5).
3. Себестоимость внесена (П3.7).
4. Цена со скидкой не ниже себестоимости — иначе нужна одобренная заявка владельца (П9). Продавец себестоимость не видит; сообщение: «Цена ниже допустимой. Нужна заявка владельцу».
5. Скидка в пределах лимита или одобрена заявкой.
6. Аксессуаров хватает на остатке магазина (Допущение: продажа «в минус» запрещена; если физически товар есть, а в системе нет — сначала приход или ревизия).
7. Сумма оплат = сумма чека.
8. Открыта смена (П1).

### 8.4 Печать и отправка

- Нефискальный чек (58/80 мм): магазин, № чека, дата, продавец, позиции с IMEI, скидка, оплаты, сдача, бонусы начислено/списано, гарантия, QR-ссылка на электронный чек. Казахский + русский.
- Гарантийный талон (A4 или чековая лента — настройка): модель, IMEI 1/2, `PM-код`, дата продажи, срок «гарантия до 09.11.2027», условия (текст из настроек; шаблон «новый 12 мес / б/у 1 мес»), подписи.
- «Отправить в WhatsApp» — ссылка на электронный чек и талон (страница без входа, по секретной ссылке; Допущение: ссылка не содержит персональных данных в адресе).
- Печать можно повторить из «Чеков» (каждая перепечатка в журнале аудита).

### 8.5 Что пишется в журналы

- `inventory_movements`: списание каждого экземпляра/аксессуара с себестоимостью на момент продажи.
- `money_entries`: по каждой строке оплаты на свой счёт; сдача — минус из кассы ₸ (или «Внесено» минус сдача одной записью, Допущение); комиссия банка — отдельная запись расхода по статье «Комиссия банка».
- `debt_entries`: долг клиента, если есть.
- `bonus_entries`: списание; начисление со статусом «ожидает активации» (П16).
- Экземпляр: статус `продан`, гарантия до даты; сайт обновится.

### 8.6 Исключения и ошибки при скане

| Ситуация | Сообщение | Что можно сделать |
|---|---|---|
| IMEI не найден | «Такого телефона нет на складе фирмы» | приход (если права) или проверить IMEI |
| Продан | «Продан 12.10.2026 (Дана, ПРД-2026-000456), гарантия до 12.10.2027» | открыть чек, оформить возврат |
| В корзине у другого | «Уже в корзине у Айдара (осталось 12 мин)» | попросить Айдара убрать; админ может снять резерв |
| В заказе | «Забронирован по заказу ЗАК-2026-000031 до 11.11 (Асель, предоплата 50 000 ₸)» | продать можно только из заказа |
| В пути / на подготовке / на проверке / брак | «Телефон в пути в магазин …» и т.п. | — |
| В другом магазине фирмы | «Телефон числится в магазине …» | Допущение: продать нельзя, сначала перемещение (П20) |
| Нет госбазы | окно П5 | отметить |
| Резерв истёк, пока продавец оформлял | при оплате — повторная проверка: если телефон ещё свободен, резерв продлевается сам; если занят — ошибка | |

### 8.7 Примеры

**А. Простая продажа с наличными и сдачей.** iPhone 15 Pro 256 — 489 000 ₸, чехол 4 990 ₸, стекло 2 990 ₸. Итого 496 980 ₸. Внесено 500 000 ₸ → сдача 3 020 ₸. Касса ₸ +496 980 ₸. Клиент выбран, бонусы (Допущение: 1% на телефоны, 3% на аксессуары, П16): 489 000 × 1% = 4 890 ₸ + 7 980 × 3% = 239 ₸ (округление вниз) = 5 129 ₸, активируются через 14 дней.

**Б. Сплит + trade-in + рассрочка.** iPhone 16 Pro 256 — 589 000 ₸.
- Trade-in iPhone 13 128 — 150 000 ₸ (П12).
- Kaspi рассрочка 12 мес — 400 000 ₸, комиссия 12% (не проверено, настройка) = 48 000 ₸.
- Наличные — 39 000 ₸.
- Итого оплат: 150 000 + 400 000 + 39 000 = 589 000 ₸ ✔.
- Прибыль по чеку: 589 000 − себестоимость 498 000 − комиссия 48 000 = 43 000 ₸.
- Журналы: телефон списан; iPhone 13 оприходован (себестоимость 150 000 ₸, `на подготовке`); счёт рассрочки +400 000 ₸ и −48 000 ₸ «Комиссия банка»; касса ₸ +39 000 ₸.

**В. Скидка сверх лимита.** Клиент просит 15 000 ₸ скидки, лимит Даны 5 000 ₸. Дана нажимает «Запросить» → Кайрату на iPhone пуш «Дана: скидка 15 000 ₸ на iPhone 15 Pro 256 (489 000 → 474 000 ₸), прибыль после скидки 51 700 ₸» → «Разрешить» → у Даны чек разблокирован за ~20 с.

**Г. В долг.** Samsung A55 — 229 000 ₸: 100 000 ₸ наличными, 129 000 ₸ в долг до 09.12.2026. Клиент обязателен. Долг клиента +129 000 ₸ (П14).

### 8.8 Услуги, подарки и продажи через Kaspi Магазин

Добавлено при сверке разделов (в магазинах телефонов это ежедневные операции, а в процессах их не было).

**Услуги** (поклейка стекла, перенос данных, настройка телефона, доставка). Это позиция справочника с признаком «услуга»: у неё нет остатка и штрихкода, цена в «Прайсе», себестоимость — 0 или фиксированная (например, работа мастера 500 ₸). Добавляется в чек плиткой «Услуги» или поиском. Бонусы — по ставке аксессуаров. Журнал товара не пишется (раздел 02, операция № 50). Пример: стекло 2 990 ₸ + поклейка 1 000 ₸ = 3 990 ₸.

**Подарок к покупке.** Владелец заводит акцию «к iPhone 16 — чехол в подарок» (Склад → Прайс → Акции; Допущение). В чеке строка чехла с ценой 0 ₸ и пометкой «Подарок»: товар списывается со склада, его себестоимость уменьшает прибыль чека, лимит скидки продавца не тратится. Подарок без акции — это скидка 100 % на строку и проверяется лимитом скидки (раздел 02, операция № 51). Пример: iPhone 16 128 — 459 000 ₸, чехол 4 990 ₸ в подарок (себестоимость 1 183 ₸) → выручка 459 000 ₸, прибыль чека меньше на 1 183 ₸.

**Продажа через Kaspi Магазин (до интеграции, этап 9).** Если телефон выставлен и в Kaspi Магазине, его можно продать дважды — в магазине и на Kaspi. Правило на 1.0 (Допущение, вопрос 23): Kaspi-заказ продавец оформляет в нашей кассе как обычную продажу с источником «Kaspi Магазин» и способом оплаты «Kaspi Магазин» (комиссия Kaspi — настройка счёта, не проверено), а при поступлении заказа сразу бронирует телефон (П10.2), чтобы его не продали в зале. Снять товар с Kaspi после продажи в зале продавец делает вручную в кабинете Kaspi; ночная сводка напоминает списком «продано у нас, но может висеть на Kaspi» (по моделям с отметкой «есть на Kaspi»).

## П9. Заявки владельцу (разрешить / отклонить)

**Кто:** создаёт любой сотрудник; решает владелец. Если владелец не ответил за 5 минут — заявку видит и может решить админ, но только в пределах **своих** лимитов; заявки «ниже себестоимости», «выгрузка клиентов», «увольнение», «допуск интегратора», «новое устройство админа» — только владелец (тайминги и правила — раздел 03, п. 6.4–6.6). **Где:** у продавца — кнопка в месте, где сработал лимит; у владельца — пуш на iPhone и блок «Заявки» на «Статистике» (макет `iphone-vladelec-1-statistika.png`).

### Типы заявок

| Тип | Когда создаётся | Что видит владелец |
|---|---|---|
| Скидка сверх лимита | П8 шаг 7 | товар, цена, скидка, итог, прибыль после скидки |
| Продажа ниже себестоимости | П8.3 п.4 | цена, себестоимость, убыток |
| Возврат | П11 (продавец) | чек, причина, сумма, способ возврата |
| Расход сверх лимита | П17 | статья, сумма, фото чека |
| Отмена (сторно) документа | любая операция, где у роли нет сторно | документ, причина |
| Выкуп б/у дороже сетки | П12 | модель, состояние, сумма, подсказка цены |
| Продажа без отметки госбазы | только если владелец включил такое правило | телефон, причина |

### Шаги

1. Сотрудник нажимает «Отправить заявку», пишет причину (необязательно для скидки, обязательно для возврата и сторно).
2. Владелец получает пуш (PWA) и Telegram (Допущение: дубль в Telegram, потому что PWA-пуши на iPhone могут не доходить, если приложение не открывалось давно). Через 3 минуты без ответа — повторный пуш, через 5 минут — заявка видна админу (см. «Кто»).
3. «Разрешить» / «Отклонить» (с причиной) / «Разрешить с изменением» (например, скидку 10 000 вместо 15 000).
4. Ответ мгновенно появляется у сотрудника; действие разблокируется **только для этого чека и этой суммы** и только на 15 минут (раздел 03, п. 6.4).
5. Срок жизни заявки — 30 мин (Допущение); после — «Истекла», можно отправить снова.

### Правила

- Одобрение не проводит документ само: проводит сотрудник. Если он изменил чек после одобрения (добавил товар, поменял цену) — одобрение сгорает, нужна новая заявка.
- Все заявки и ответы — в журнале аудита и отчёте «Заявки за период».

## П10. Резерв и заказ с предоплатой

### 10.1 Резерв в корзине (короткий)

Автоматически на 30 минут при добавлении телефона в корзину (П8, шаг 3). Снимается сам по таймеру, при удалении из корзины или при проведении продажи. Админ может снять чужой резерв («Освободить», с записью в аудит).

### 10.2 Заказ (бронь) с предоплатой

**Кто:** продавец, админ. **Где:** «Продажа → Заказы → Новый заказ» или из корзины кнопкой «Оформить как заказ».

**Откуда приходят:** клиент написал в WhatsApp с сайта (кнопка на карточке) или пришёл в магазин. Сайт сам заказов с персональными данными не принимает (архитектура 4: без форм с персональными данными) — бронь оформляет продавец по переписке.

#### Шаги

1. Клиент (обязателен: имя, телефон, согласие).
2. Что бронируем:
   - **конкретный телефон** (скан IMEI / `PM-код`) — он сразу получает статус `забронирован по заказу` (`ordered`);
   - **вариант, которого нет** («под заказ»: модель, память, цвет) — без экземпляра.
3. Срок брони (по умолчанию 3 дня, Допущение), цена (фиксируется на момент заказа).
4. Предоплата (необязательна): сумма и способ (нал / Kaspi / …). Предоплата — деньги в кассе/на счёте + **аванс клиента** (наш долг клиенту, запись в `debt_entries` со знаком «мы должны»).
5. Печать/отправка в WhatsApp «Квитанции о предоплате».
6. Когда клиент пришёл — «Продать по заказу»: заказ открывается в корзине, предоплата встаёт строкой оплаты, доплата — любым способом (П8).
7. Для «под заказ»: при приходе (П3) телефона этого варианта система подсказывает «Есть заказ ЗАК-2026-000031 на этот вариант. Привязать?» → экземпляр в резерв по заказу, клиенту — шаблон сообщения в WhatsApp «Ваш телефон пришёл».

#### Исключения

| Ситуация | Правило |
|---|---|
| Срок брони истёк | **Без предоплаты** — бронь снимается сама, телефон снова `в наличии`. **С предоплатой** — заказ «Просрочен», уведомление продавцу и владельцу; бронь сама не снимается, продавец звонит клиенту и продлевает или отменяет (раздел 02, п. 10.3) |
| Отмена с предоплатой | Возврат предоплаты тем же способом; Допущение: удержаний нет; удержание — только заявкой владельцу |
| Цена изменилась после заказа | Продаётся по цене заказа; если снизилась — по новой (в пользу клиента, Допущение) |
| Клиент берёт другой телефон | Заказ «Изменить»: снять резерв со старого, поставить на новый; предоплата переносится |

#### Пример

Асель бронирует iPhone 16 Pro Max 256 Desert (`PM-10530`, 699 000 ₸) на 2 дня, предоплата 50 000 ₸ Kaspi QR. Kaspi QR +50 000 ₸, аванс клиента 50 000 ₸. Через день: продажа по заказу — предоплата 50 000 + рассрочка Kaspi 649 000 ₸ = 699 000 ₸. Аванс закрыт.

## П11. Возврат и обмен

**Закон (не проверено, [`00-kazakhstan.md`](00-kazakhstan.md), п. 8):** телефоны надлежащего качества — в перечне невозвратных (с 2019 г., актуальность на 2026 сверить); аксессуары — по общему правилу 14 дней; при онлайн-продаже с доставкой, возможно, 14 дней действуют и для телефонов; брак — замена или деньги, сроки 10/30 дней.

**Кто:** админ, владелец — проводят; продавец — оформляет и отправляет заявку (архитектура 3). **Где:** «Продажа → Возврат» (F10) или «Чеки → чек → Возврат».

### 11.1 Шаги возврата

1. Найти продажу: скан IMEI проданного телефона, номер чека, телефон клиента или QR с чека.
2. Отметить строки к возврату (телефон, аксессуары частично по количеству). Возврат — только в рамках одного чека.
3. **Причина** (обязательна, список):
   - брак (подтверждён проверкой) — П13 решает, если нужна экспертиза;
   - не подошёл (аксессуар, ≤ 14 дней);
   - онлайн-покупка, ≤ 14 дней (если юрист подтвердит);
   - ошибка продавца (пробили не то);
   - по решению владельца (вне закона) — только заявкой.
4. Состояние возвращённого: «Целый, в продажу» / «На проверку» / «Брак». Для телефона — повторный чек-лист (iCloud/FRP отвязан, комплект, внешний вид).
5. **Сумма к возврату** считается сама — по цене продажи со скидкой. Можно уменьшить (удержание за комплект) — только с заявкой. Предупреждение, если сумма отличается от цены продажи (как в sfon).
6. **Как вернуть деньги** — по умолчанию теми же способами, что платили (Допущение: в обратном порядке: сначала уменьшаем долг клиента, потом бонусы, потом безнал, потом наличные):
   - долг клиента → долг уменьшается (денег не отдаём);
   - бонусы, которыми платили → восстанавливаются;
   - Kaspi / карта → возврат делается в приложении Kaspi Pay / терминале, в системе — запись со ссылкой на исходную оплату;
   - рассрочка банка → оформление возврата через банк (номер договора), в системе — запись «возврат по рассрочке»; комиссия банка по умолчанию **не возвращается** и остаётся расходом (раздел 02, вопрос 4; вернёт ли банк комиссию — не проверено). Если банк вернул — отдельная запись дохода по статье «Комиссия банка»;
   - зачёт trade-in → Допущение: клиенту возвращаются деньги на сумму зачёта (сданный им телефон остаётся у магазина), либо, если сданный телефон ещё не продан и клиент хочет, — возвращается сам телефон (документ «Отмена trade-in»);
   - наличные → из кассы ₸ (проверка: в кассе хватает денег).
7. Начисленные за покупку бонусы аннулируются (если ещё не активированы — просто отменяются). Если уже активированы и потрачены, а баланса не хватает — недостающие бонусы **удерживаются из суммы возврата деньгами** (1 бонус = 1 ₸), продавец видит это в форме возврата. Баланс бонусов в минус не уходит (раздел 02, п. 6.5 и 11.7).
8. Продавец: «Отправить заявку» (П9). Админ: «Провести» в пределах лимитов L7–L9 раздела 03 (по умолчанию телефон до 600 000 ₸ и до 14 дней после продажи), сверх — заявка. Владелец: «Провести» без ограничений.
9. Печать «Акта возврата» (kk/ru) с подписью клиента; фискальный чек возврата — в приложении кассы, номер в поле.

### 11.2 Что происходит с товаром

| Состояние при возврате | Статус телефона | Сайт |
|---|---|---|
| Целый, в продажу | `в наличии` (тот же экземпляр, история продолжается) | показ включается по прежней настройке |
| На проверку | `на проверке` (`on_check`) → решение позже: в продажу / на подготовку / брак (кнопка «Решение по проверке», админ/владелец) | нет |
| Брак | `брак` → возврат поставщику (П15) или ремонт (П6) или списание (П22) | нет |

Аксессуар: «целый» — обратно на остаток по себестоимости продажи; «брак» — сразу на «Списание» или «Возврат поставщику».

### 11.3 Обмен

Обмен = возврат + новая продажа **на одном экране** («Обмен»):
1. Найти старую продажу, отметить, что сдают (как 11.1).
2. Отсканировать новый товар.
3. Разница: если новый дороже — клиент доплачивает (П8.2); если дешевле — разницу возвращаем (как 11.1, шаг 6).
4. Проводится двумя документами (`ВЗК-…` и `ПРД-…`), связанными между собой, в одной транзакции.

### 11.4 Ошибки

| Ситуация | Сообщение |
|---|---|
| Чек уже полностью возвращён | «По чеку ПРД-2026-000456 всё возвращено 15.10.2026» |
| В кассе меньше денег, чем вернуть | «В кассе 120 000 ₸, нужно 229 000 ₸. Верните на Kaspi или частично из сейфа» |
| Телефон надлежащего качества, прошло больше 14 дней, причина «не подошёл» | «Телефон надлежащего качества по закону не возвращается (не проверено). Возврат только по решению владельца» → заявка |
| Возврат в другом магазине фирмы | Допущение: можно, деньги из кассы того магазина, где возвращают |

### 11.5 Примеры

**А. Возврат брака по аксессуару.** Зарядка 7 990 ₸ куплена 3 дня назад за наличные, не заряжает. Причина «брак», состояние «Брак». Касса ₸ −7 990 ₸; зарядка на «Брак» → «Возврат поставщику». Бонус 239 ₸ (неактивированный) сгорает.

**Б. Обмен телефона.** Клиент купил Samsung A55 за 229 000 ₸ (100 000 нал + 129 000 долг), на 2-й день телефон завис — экспертиза подтверждает брак. Обмен на A55 другого цвета, 229 000 ₸. Возврат: долг −129 000, нал 100 000 ₸ — но вместо выдачи денег на экране «Обмен» они идут в новый чек: новая продажа 229 000 = 100 000 зачёт + 129 000 в долг с той же датой. Деньги из кассы не выходят. Старый телефон — `брак`.

## П12. Trade-in: зачёт в покупку и выкуп за деньги

**Кто:** продавец (принимает, при сумме в пределах сетки), админ/владелец (сверх сетки — заявка П9). **Где:** в кассе F8 (зачёт в покупку) или «Склад → Trade-in → Выкуп» (выкуп за деньги без покупки). На iPhone — то же.

### 12.1 Шаги

1. **Устройство:** модель из справочника (поиск), память, цвет; IMEI — скан коробки или **набрать `*#06#`** на телефоне и сверить (галочка «IMEI сверен с *#06#» обязательна).
2. **Проверка IMEI:**
   - 0.3 (Луна, дубли). Если IMEI есть в фирме — это тот же экземпляр (например, мы его когда-то продали): история продолжается, в паспорте видно «продан нами 12.03.2026, клиент …».
   - **Госбаза — обязательно до выплаты** (П5). «Не верифицирован» / «Заблокирован» → приём запрещён, акт не проводится.
3. **Чек-лист приёма** ([`00-analogi.md`](00-analogi.md), п. 5), все пункты обязательны:
   - iCloud / «Локатор» выключен (Android — аккаунт Google / FRP отвязан) — **без этой галочки акт не проводится**;
   - экран (трещины, битые пиксели), корпус, вода (индикатор), Face ID / Touch ID, камеры, динамики, микрофон, зарядка, кнопки, Wi-Fi/Bluetooth, SIM;
   - батарея % (из настроек телефона);
   - заменённые детали (iPhone показывает «Неизвестная деталь»);
   - комплект (коробка, кабель).
4. **Грейд** A/B/C (подсказка по чек-листу) и **фото** (минимум 2: перед, зад; на iPhone — сразу камерой).
5. **Оценка:** подсказка из «Сетки выкупа» (владелец задаёт базовую цену на вариант и скидки за дефекты; архитектура 7, этап 8) + история 90 дней (П6, шаг 5). Сумма вводится вручную. Если сумма > сетки (Допущение: больше чем на 5%) или сетки нет — заявка владельцу (П9).
6. **Продавец телефона (физлицо):** ФИО, ИИН (12 цифр, проверка контрольной цифры, Допущение), номер удостоверения, телефон, согласие на обработку данных (дата, способ, версия текста — [`00-kazakhstan.md`](00-kazakhstan.md), п. 2). ИИН хранится зашифрованно, после сохранения виден только владельцу и админу, остальным — `********1234` (архитектура 2.9). Скан удостоверения не храним. Если человек уже есть в клиентах (по телефону или отпечатку ИИН) — подставляется.
7. **Способ:**
   - **Зачёт в покупку** — сумма встаёт строкой оплаты «Trade-in» в текущем чеке (П8).
   - **Выкуп за деньги** — выплата из кассы ₸ (проверка остатка кассы) или переводом Kaspi (номер операции).
8. **Акт trade-in** (kk/ru) — печать, подпись сдающего и продавца. Без отметки «Акт подписан» документ проводится, но висит в списке «Акты без подписи» (Допущение).
9. **Проведение:** экземпляр приходуется как б/у, себестоимость = сумма зачёта/выкупа, статус `на подготовке` (П6), поставщик — «Trade-in: ФИО». Деньги: выкуп — минус из кассы; зачёт — запись в продаже.

### 12.2 Особые случаи

| Ситуация | Правило |
|---|---|
| Сумма зачёта больше суммы покупки | Разница выплачивается клиенту из кассы (или Kaspi) в том же чеке: пример — сдаёт за 200 000 ₸, покупает чехол и стекло на 7 980 ₸ → выдать 192 020 ₸ |
| Клиент передумал после проведения акта | Сторно акта (админ), если телефон ещё `на подготовке` и деньги возвращены |
| Повторный trade-in (телефон, который мы продавали) | тот же экземпляр, ИИН нового сдающего пишется в новый акт |
| Сдаёт не владелец (на чужой телефон) | Допущение: в акте галочка «Я являюсь собственником устройства» и предупреждение об ответственности (текст — юристу) |
| Телефон с блокировкой оператора / в рассрочке у банка | Допущение: пункт чек-листа «не в залоге/рассрочке» со слов клиента |

### 12.3 Пример

Клиент сдаёт iPhone 13 128 Midnight: батарея 79%, грейд B, всё работает, iCloud выключен, госбаза «Верифицирован». Сетка: 165 000 ₸, −15 000 за батарею < 80% = 150 000 ₸. Продавец ставит 150 000 ₸ (в пределах сетки, заявка не нужна). Зачёт в покупку iPhone 16 Pro (П8, пример Б). Новый экземпляр `PM-10517`, себестоимость 150 000 ₸, `на подготовке`. Дальше П6: батарея 18 000 ₸ → себестоимость 168 000 ₸ → цена 219 000 ₸ → сайт (П4).

## П13. Гарантийный случай и ремонт

Допущение: магазин сам не ремонтирует, а отправляет в сервис-партнёр (или в авторизованный сервис производителя); платный ремонт не по гарантии — позже. Сроки «10 дней на ремонт, до 30 дней на экспертизу/решение» — по пересказам закона, не проверено ([`00-kazakhstan.md`](00-kazakhstan.md), п. 8).

**Кто:** продавец (приём), админ/владелец (решение). **Где:** «Продажа → Гарантия» (список обращений) и паспорт телефона → «Гарантийное обращение».

### Шаги

1. Клиент приносит телефон. Скан IMEI → паспорт: «Продан 12.10.2026, Асель, гарантия до 12.10.2027 ✔» (или «Гарантия закончилась 12.11.2026» — красным; можно принять платно, Допущение: позже).
2. «Новое обращение»: жалоба (текст + быстрые варианты: не включается, не заряжается, экран, камера, звук, сеть), внешний вид при приёме, комплект, фото (2+), пароль/код — **не храним**, просим клиента выйти из iCloud или оставить телефон без пароля (Допущение).
3. Печать «Квитанции о приёме» (kk/ru) с номером `ГРО-2026-000012` и датой; клиенту — ссылка в WhatsApp на статус.
4. Статус телефона **не меняется** — остаётся `продан` (телефон принадлежит клиенту). В паспорте и в списке обращений — флажок «на гарантии у нас» с номером `ГРО-…`; журнал товара не пишется (раздел 02, операция № 46). Ревизия (П21) показывает такие телефоны отдельной строкой «на гарантии», чтобы их не считали лишними.
5. Отправка в сервис: кому, когда, номер квитанции сервиса. Счётчики дней на экране обращения: «в работе 6 из 10 дней», «до решения 24 дня».
6. Решение (админ/владелец):
   - **Отремонтирован** → «Выдан клиенту» (подпись), флажок «на гарантии у нас» снимается, гарантия продлевается на срок ремонта (Допущение);
   - **Замена** → П11.3 «Обмен» (сданный — `брак`);
   - **Возврат денег** → П11 (причина «брак»);
   - **Отказ** (не гарантийный случай: вода, удар) → «Выдан без ремонта», причина и заключение сервиса (фото).
7. Затраты на ремонт по гарантии: если платит поставщик — долг поставщика нам; если магазин — расход «Гарантийный ремонт» (П17), привязанный к экземпляру (в отчёте прибыли по телефону).

### Пример

Асель приносит iPhone 15 Pro (`PM-10482`), куплен 12.10.2026, не заряжается. `ГРО-2026-000012` 09.11, отправлен в сервис «Apple-Сервис Шымкент» 10.11. 14.11 — замена разъёма бесплатно от поставщика. Выдан 15.11. Гарантия до 12.10.2027 + 6 дней = 18.10.2027 (Допущение).

## П14. Долги клиентов

**Кто:** продавец (выдать в долг в чеке, принять оплату), админ/владелец (корректировка, сторно). **Где:** «Долги → Клиенты», карточка клиента, на iPhone владельца — плитка «Должны нам».

### 14.1 Возникновение

Только через продажу (строка оплаты «В долг», П8) или ручной документ «Корректировка долга» с основанием (только админ/владелец). Обязательны клиент и дата возврата. Два разных лимита (Допущение, значения — раздел 03, п. 5.1):
- **лимит роли** «Новый долг клиенту» (L4) — до какого **общего** долга клиента сотрудник даёт в долг сам: продавец 100 000 ₸, старший продавец 300 000 ₸, админ 1 000 000 ₸, срок до 30 дней (L5); новому клиенту и клиенту с просроченным долгом — только заявкой;
- **потолок фирмы** «Максимальный долг одного клиента» (настройка, по умолчанию 300 000 ₸) — выше него не даёт в долг никто, кроме владельца; сотрудник получает кнопку «Запросить у владельца».

Пример: у Асхата долг 70 000 ₸, Дана продаёт ему чехол в долг на 40 000 ₸ → общий долг 110 000 ₸ > 100 000 ₸ (лимит продавца) → заявка.

### 14.2 Частичная оплата долга

1. «Долги → Клиенты» → клиент (или поиск в кассе F4 → «Погасить долг»).
2. Сумма (любая ≤ долга), способ (нал / Kaspi / карта; комиссия по счёту), примечание.
3. Если у клиента несколько долгов — гасится самый старый первым (Допущение); можно выбрать конкретный чек.
4. Проведение: `money_entries` +сумма; `debt_entries` −сумма. Печать квитанции «Оплата долга» с остатком.
5. Начисление бонусов на оплаченную часть долга — при погашении (Допущение, П16).

### 14.3 Напоминания

| Когда | Кому | Что |
|---|---|---|
| за 1 день до срока, 09:00 | продавцу, который выдал, и владельцу | «Завтра срок: Ерлан, 129 000 ₸» |
| в день срока | им же | список «Сегодня срок» на главной |
| просрочка | владельцу ежедневно в 09:00 — строкой в утренней сводке «Итог вчера» (раздел 06, п. 4.1) | «Просрочено 3 долга на 312 000 ₸» |
| по кнопке | клиенту | «Напомнить в WhatsApp» — открывает WhatsApp с готовым текстом: «Здравствуйте, Ерлан! Напоминаем о платеже 129 000 ₸ по покупке от 09.11.2026 в Prime Mobile. Срок — 09.12.2026» |

Цвета срока как в sfon: больше 5 дней — обычный, меньше 5 дней — жёлтый, меньше 1 дня — оранжевый, просрочено — красный.

### 14.4 Пример

Ерлан: долг 129 000 ₸ до 09.12. 25.11 платит 50 000 ₸ Kaspi QR → остаток 79 000 ₸. 08.12 напоминание. 10.12 — красный «просрочено 1 день», Кайрат жмёт «Напомнить в WhatsApp». 12.12 Ерлан платит 79 000 ₸ наличными → долг 0.

## П15. Долги поставщикам и возврат поставщику

**Кто:** админ, владелец. **Где:** «Долги → Поставщики».

### 15.1 Возникновение

Приход «в долг» или «частично» (П3, П7), затраты подготовки в долг мастеру (П6). Долг хранится **в валюте прихода**: в $ остаётся в $ (архитектура 2.8).

### 15.2 Оплата (частичная)

1. Поставщик → «Оплатить»: сумма, валюта оплаты, счёт (касса $, касса ₸, Kaspi Gold, сейф).
2. Если валюта оплаты ≠ валюте долга: система показывает пересчёт по **текущему курсу** (можно ввести курс сделки с поставщиком). Долг уменьшается в своей валюте.
3. Проверка: на счёте хватает денег.
4. Курсовая разница (себестоимость записана по курсу прихода, оплата — по курсу дня) — в отчёте «Курсовые разницы», себестоимость телефонов не меняется (Допущение).

### 15.3 Напоминания

За 3 дня до срока и в день срока — владельцу (Допущение). Сводка «Мы должны» на главной владельца.

### 15.4 Возврат поставщику

1. «Склад → Возврат поставщику»: поставщик, скан IMEI (только `в наличии`, `брак`, `на проверке`) или аксессуары с количеством, причина.
2. Сумма возврата по себестоимости (можно другую — договорённость).
3. Как компенсирует поставщик: уменьшает наш долг / возвращает деньги / даёт замену (новый приход).
4. Экземпляр → `возвращён поставщику`; если вернут отремонтированным — тот же IMEI возвращается приходом и **продолжает историю** (П3.7).

### 15.5 Пример

Долг «Мобайл-Трейд» $8 200 (приход по 515). 16.11 платим 2 000 000 ₸ с Kaspi Gold по курсу 520 → $3 846,15. Остаток $4 353,85. 20.11 платим $4 353,85 из кассы $ → долг 0. Курсовая разница: 3 846,15 × (520 − 515) = 19 230,75 ₸ в отчёте.

## П16. Бонусы

Правила как в sfon: отдельный % на телефоны и аксессуары, дни до активации ([`00-sfon-paritet.md`](00-sfon-paritet.md), п. 11.2). Значения — Допущения, их задаёт Кайрат в «Настройки → Бонусы».

| Параметр | По умолчанию (Допущение) |
|---|---|
| % на телефоны (новые) | 1% |
| % на телефоны б/у | 1% |
| % на аксессуары | 3% |
| Дней до активации | 14 |
| Максимум списания | 20% суммы чека |
| Срок жизни бонусов | 365 дней с активации |
| На что начисляются | на часть чека, оплаченную деньгами (нал, Kaspi, карта, рассрочка банка); **не** на бонусы, trade-in и долг (на долг — при погашении) |
| Подтверждение списания кодом | выключено |

### Шаги

1. Начисление — при проведении продажи, статус «ожидает активации» до даты.
2. Активация — ночью автоматически. Клиенту — сообщение (WhatsApp/SMS — по настройке; позже).
3. Списание — в кассе (П8, шаг 6), 1 бонус = 1 ₸.
4. Возврат — П11, шаг 7.
5. Ручная корректировка (подарок, исправление) — админ/владелец, документ с причиной.
6. Сгорание по сроку — ночью, запись в журнале.

### Пример

Покупка 496 980 ₸ наличными → +5 129 бонусов, активны с 23.11. 01.12 клиент покупает чехол 4 990 ₸: можно списать ≤ 998 ₸ (20%) → списал 998, доплатил 3 992 ₸ наличными, начислено 3 992 × 3% = 119 бонусов.

## П17. Расходы

**Кто:** продавец — из кассы своего магазина (по настройке роли и в пределах лимита); админ, владелец — любые. **Где:** «Расходы» (ноутбук, iPhone).

### Шаги

1. «+ Расход»: статья (аренда, зарплата, обед, такси, реклама Instagram, ремонт б/у, комиссия банка — автоматическая, регистрация IMEI, хозрасходы… — список из настроек, перенос из sfon), сумма, валюта.
2. Откуда платим — одна или **несколько строк** (часть наличными, часть со счёта, как в sfon): касса ₸, касса $, Kaspi Gold, сейф.
3. Описание, фото чека (камера iPhone), магазин, дата (сегодня; прошлой датой — админ и владелец, не раньше 3 дней и не в закрытом месяце, с причиной; раздел 02, п. 9.2, право `doc.backdate` раздела 03).
4. Проверки: денег на счёте хватает; сумма ≤ лимита роли (Допущение: продавец — 10 000 ₸ за раз и 20 000 ₸ в день, лимиты L10–L11 раздела 03), иначе заявка (П9).
5. Проведение: `money_entries` минус по каждому счёту.
6. Отмена — сторно с причиной (админ/владелец).

### Пример

Обед продавцам 6 000 ₸ из кассы ₸ (Дана, в лимите). Реклама Instagram 45 000 ₸: 20 000 нал + 25 000 Kaspi Gold — Дана отправляет заявку, Кайрат разрешает, Дана проводит.

## П18. Инкассация, переводы между кассами, обмен валюты

### Счета (настраиваются; Допущение по составу)

| Счёт | Валюта | Где |
|---|---|---|
| Касса ₸ магазина | ₸ | магазин |
| Касса $ магазина | $ | магазин |
| Сейф ₸ и Сейф $ (Центральная касса) | два счёта: ₸ и $ (каждый счёт в одной валюте, раздел 02, п. 3.4) | фирма (у владельца) |
| Kaspi Gold, Kaspi QR, терминал, счёт ИП | ₸ | фирма, с комиссией по умолчанию |
| Рассрочки банков (транзитные) | ₸ | фирма |

### 18.1 Инкассация (касса магазина → сейф / владелец)

1. Админ/продавец: «Баланс → Инкассация»: из какой кассы, сумма ₸ и/или $, кому (сейф / Кайрат лично), комментарий.
2. Документ в статусе «отправлено». Деньги в кассе магазина уменьшаются сразу, «в пути» — до подтверждения.
3. Владелец на iPhone «Принять 300 000 ₸ от Даны» → деньги в сейфе. Если сумма не та — «Принять другую сумму» с комментарием → расхождение в отчёт смен (Допущение).
4. Нельзя инкассировать больше остатка кассы.

**Пример:** вечером в кассе 714 480 ₸ → инкассация 600 000 ₸ → в кассе 114 480 ₸ на размен (те же цифры, что в П19). Кайрат принял 600 000 ₸ в 21:15.

### 18.2 Перевод между счетами

Kaspi Gold → касса (снятие), касса → Kaspi (внесение), сейф → касса магазина (размен). Один документ, две записи. Комиссия за снятие — строка расхода (необязательно).

### 18.3 Обмен валюты

1. «Баланс → Обмен валюты»: из ($ / ₸), в (₸ / $), сумма, курс сделки (по умолчанию курс дня).
2. Две записи по курсу (архитектура 2.8).
3. **Доллары от покупателя не принимаются** (архитектура 2.8, Д6; раздел 02, п. 3.4). Обмен валюты — только внутренний документ фирмы (касса $ ↔ касса ₸ / сейф, обмен в обменнике). Покупать $ у клиента в счёт чека — нельзя: обмен валюты для населения в РК, по пересказам, требует лицензии обменного пункта (не проверено). Если Кайрат ответит иначе (вопрос 8), включается настройка «Покупка $ у клиента» с курсом «курс дня − 3 ₸» — по умолчанию она **выключена**.

**Пример:** вечером в кассе $ лежит $1 000. Ержан меняет их в обменнике по 512 при курсе фирмы 515: документ «Конвертация» — касса $ −$1 000 (515 000 ₸ по курсу фирмы), касса ₸ +512 000 ₸, курсовая разница −3 000 ₸ (раздел 02, п. 3.4).

## П19. Закрытие смены и сверка кассы

**Кто:** продавец (последний в смене), админ. **Где:** «Продажа → Закрыть смену».

### Шаги

1. Система показывает итоги смены: продажи (кол-во, сумма), возвраты, по способам оплаты (нал, Kaspi QR, Kaspi Gold, терминал, рассрочки, долг, бонусы, trade-in), расходы, инкассации, выкуп trade-in.
2. «Должно быть в кассе ₸» и «в кассе $» = начало смены + приход − расход по журналу.
3. Продавец пересчитывает и вводит факт (можно по купюрам).
4. **Сверка безнала (Допущение):** сумма Kaspi QR за смену в системе против итога в приложении Kaspi Pay — продавец вводит итог из Kaspi; расхождение подсвечивается (полная сверка по выписке — позже, [`00-kazakhstan.md`](00-kazakhstan.md), п. 6).
5. Проверки перед закрытием: нет корзин с резервом, нет черновиков продаж (предупреждение, не запрет); продажи без номера фискального чека — список (предупреждение).
6. Расхождение ≠ 0 → обязательный комментарий; владельцу пуш «Смена закрыта: недостача 2 000 ₸ (Дана)».
7. Расхождение **сразу** пишется документом смены (`СМН-…`) по статье «Недостача/излишек кассы» — журнал совпадает с деньгами в ящике (раздел 02, п. 8). Больше 1 000 ₸ — владельцу задача «разобрать»: «Принять» (ничего не меняется) или «Удержать с сотрудника» (Допущение: отметка в отчёт по сотруднику, без расчёта зарплаты).
8. Смена закрыта, отчёт смены (печать/PDF). Если смену не закрыли до 23:59 — владельцу сигнал «Касса не закрыта» (архитектура 6), смена закрывается вечером автоматически без пересчёта со статусом «не сверена» (Допущение).

### Пример

Начало 184 500 ₸. Продажи наличными 496 980 + 39 000, сдача уже учтена; расход обед −6 000; выкуп trade-in −0; инкассация −600 000. Должно: 184 500 + 535 980 − 6 000 − 600 000 = 114 480 ₸. Факт 114 480 ₸ → «Сходится», смена `СМН-2026-000210` закрыта в 21:20. Если бы насчитали 112 480 ₸ — запись −2 000 ₸ «Недостача кассы», пуш Кайрату (больше порога 1 000 ₸).

## П20. Перемещение между магазинами (на будущее)

Сейчас один магазин; процесс нужен для второго магазина **внутри фирмы** Кайрата. Между фирмами (второй филиал — отдельная фирма) перемещения нет: это продажа одной фирмы и приход у другой (архитектура 2.1).

**Кто:** продавец (отправить/принять), админ, владелец. **Где:** «Склад → Перемещения».

### Шаги

1. Отправитель: «Новое перемещение» → магазин-получатель → скан IMEI / штрихкодов аксессуаров с количеством → комментарий → «Отправить».
2. Проверки: телефон `в наличии` в магазине-отправителе (не в резерве, не на подготовке); аксессуаров хватает.
3. Товар → `в пути`, не продаётся, на сайте скрыт (или показан с магазином «скоро в …», Допущение: скрыт).
4. Получатель видит «Входящие (1)»: сканирует пришедшее → совпало ✔ / не пришло / лишнее.
5. «Принять» → товар в магазине-получателе, `в наличии`, сайт показывает новый магазин и его WhatsApp. «Отказать» (по позиции) — с причиной, товар возвращается отправителю «в пути обратно».
6. Отправитель может «Отменить» до приёма.
7. Отчёт «Зависшие перемещения» — дольше 24 ч в пути (Допущение), сигнал владельцу.

### Пример

Из «Керуен» в «Магазин 2»: 2 × iPhone 15 Pro 256 и 10 чехлов. Принято 2 телефона и 9 чехлов, по 1 чехлу «не пришло» → отказ с причиной → 1 чехол возвращается отправителю; если не найден — списание (П22).

## П21. Ревизия сканером

**Кто:** продавцы сканируют; итог проводит админ или владелец (архитектура 2.11). **Где:** «Склад → Ревизия» (ноутбук и несколько iPhone одновременно).

### Шаги — электроника

1. «Новая ревизия»: магазин, что проверяем (все телефоны / тип / семейство / только б/у).
2. Система фиксирует «что числится» на момент старта.
3. Сканирование IMEI с нескольких устройств одновременно, каждый скан виден всем: «Отсканировано 143 из 150».
4. Продажи во время ревизии **разрешены** (Допущение): проданный после старта экземпляр исключается из «недостающих» сам.
5. Итог по трём спискам:
   - **Недостача** — числятся, но не отсканированы;
   - **Лишние** — отсканированы, но в системе нет (→ черновик прихода) или числятся в другом магазине/статусе (→ подсказка: перемещение, возврат);
   - **Не в том статусе** — например, `продан`, а лежит на полке (→ проверить возврат).
6. Повторный поиск недостающих: «Найти» — скан ещё раз.
7. «Провести итог» (админ/владелец): документ корректировки — недостающие → `списан` с причиной «недостача по ревизии РЕВ-…», лишние → приход по решению. Телефоны с флажком «на гарантии у нас» (П13) и в статусе `в пути` показываются отдельно и в недостачу не попадают. Подпись, PDF акта.

### Шаги — аксессуары

Скан штрихкода → количество растёт само; можно ввести количество руками (+ 10). Итог: учёт / факт / отклонение по каждой позиции; излишки и недостачи в деньгах по средней себестоимости.

### Пример

Ревизия б/у: числится 24, отсканировано 23. Недостаёт iPhone 12 64 (`PM-10377`). Поиск: в паспорте — «принят на гарантию»? Нет. Нашли в сейфе → скан → 24/24, итог без корректировки.

## П22. Смена цены, списание, сторно

### 22.1 Смена цены (переоценка)

1. «Склад → Прайс» (цена варианта / аксессуара) или карточка экземпляра (П4).
2. Новая цена ₸, причина (переоценка, акция, курс). Для варианта — галочка «обновить цену у оприходованных телефонов этого варианта» с предпросмотром «Изменится 7 телефонов» ([`00-sfon-paritet.md`](00-sfon-paritet.md), п. 10.2).
3. История `price_changes`: кто, когда, было/стало, причина.
4. Предложение напечатать новые ценники/этикетки.
5. Сайт обновляется сам (П4).
6. Права: владелец, админ (Допущение: продавец не меняет цены).

**Пример:** вышел iPhone 17 → iPhone 16 Pro 256 с 589 000 на 549 000 ₸, 4 экземпляра обновлены, 4 этикетки на печать, сайт — через минуту.

### 22.2 Списание

Документ «Списание»: экземпляр или аксессуар с количеством, причина (брак, разбит, потерян, на запчасти, недостача), фото, комментарий. Только админ/владелец. Себестоимость уходит в отчёт «Потери за месяц».

### 22.3 Сторно

Любой проведённый документ → «Отменить (сторно)» → причина → проверка, что сторно возможно (например, нельзя сторнировать приход, если телефон из него продан: сначала возврат продажи) → обратные записи. Продавец — только заявкой (П9). Сигнал владельцу о сторно за день (архитектура 6).
