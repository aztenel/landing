## 1. Как устроено: одна система, два адреса

Архитектура 4 и раздел «Почему один Laravel» уже решили: сайт — часть того же приложения, без отдельного API синхронизации. Здесь — детали.

| Часть | Где живёт | Кто пользуется | Что делает |
|---|---|---|---|
| **ERP** | `erp.<домен>` (Допущение: поддомен), пул PHP «касса/ERP» | сотрудники | склад, касса, фото, цены, раздел «Сайт» (п. 14) |
| **Сайт-каталог** | `<домен>` и `www.<домен>`, пул PHP «витрина» | покупатели, Google | показывает товары, ведёт в WhatsApp, создаёт анонимные заявки |
| **Публичные таблицы** | та же база PostgreSQL, отдельные таблицы `storefront_*` | читает только сайт | безопасная копия: только разрешённые поля (п. 2) |
| **Очередь `storefront`** | Redis + Horizon | фоновые задачи | пересобирает карточки, обрабатывает фото, сбрасывает кэш |
| **Хранилище фото** | диск сервера в РК: приватная папка (оригиналы) и публичная (готовые WebP) | Nginx отдаёт публичные напрямую | фото не идут через PHP |
| **Кэш страниц** | Redis (Допущение: Nginx-кэш как запасной вариант) | сайт | готовый HTML страниц, сброс по событию |

**Правило изоляции.** Код сайта подключается к базе отдельным пользователем PostgreSQL, у которого есть право **только на чтение таблиц `storefront_*`** и запись в `site_leads` / `site_stats` (Допущение: такая роль БД — надёжнее, чем договорённость в коде). Даже ошибка в шаблоне сайта не может прочитать склад, себестоимость или клиентов.

**Несколько фирм.** У каждой фирмы свой сайт на своём домене (архитектура Д2, раздел 03, п. 10). Во всех `storefront_*` есть `organization_id`; сайт определяет фирму по домену запроса. Сейчас одна фирма — Prime Mobile.

### 2.2 Аксессуары — `storefront_accessories`

Поля: публичный код (`PA-2041`, Допущение), название ru/kk, категория, бренд, совместимость (модели), фото, цена ₸, старая цена, метки, наличие **словами**: «в наличии» (остаток ≥ 1 хотя бы в одном показанном магазине) / «под заказ» (остаток 0 и у товара включено «можно под заказ») / не показывается. Количество в штуках не публикуется (архитектура 4).

### 2.4 Что не публикуется никогда

| Данные | Почему | Как гарантировано |
|---|---|---|
| IMEI 1, IMEI 2, серийный номер | по IMEI можно подделать телефон / заблокировать | поля нет в `storefront_*`; автотест: в HTML любой страницы нет 15 цифр подряд и 14 цифр подряд |
| Себестоимость, курс закупа, наценка | коммерческая тайна | поля нет; роль БД сайта не видит склад |
| Поставщик, приход, номер документа | коммерческая тайна | поля нет |
| Клиенты, телефоны, ИИН, кому продан | персональные данные (закон № 94-V, [`00-kazakhstan.md`](00-kazakhstan.md), п. 2) | поля нет; страница «Продан» не говорит кому и за сколько |
| Долги, бонусы, продавцы, кто снимал фото | внутреннее | поля нет |
| Остатки аксессуаров в штуках | внутреннее | только «в наличии / под заказ» |
| Дата и источник проверки госбазы | лишнее и помогает мошенникам | только флаг «Проверен в госбазе IMEI» |
| Статусы «брак», «на проверке», «в пути», «на подготовке» | внутреннее | такие экземпляры просто не попадают в таблицу |
| Геоданные и данные камеры в фото | могут раскрыть адрес дома владельца | EXIF удаляется при обработке (п. 3.3), автотест |
| IMEI на фото (наклейка коробки, экран «Об устройстве») | то же, что IMEI | подсказка при съёмке + модерация (п. 3.5) |
| Внутренние ID базы | облегчают перебор | на сайте только `PM-код` и slug |

## 3. Фото: «сфотографировал — появился»

### 3.1 Где можно снять или загрузить фото

| Место в ERP | Устройство | Когда удобно | Права |
|---|---|---|---|
| **Паспорт телефона → вкладка «Сайт»** (Э10.4) | iPhone, ноутбук | главный путь: скан IMEI → фото | `site.photo` (03, п. 54) |
| **Приход, после каждого скана** — кнопка «📷 Фото для сайта» (Э11, П3) | iPhone | б/у и trade-in сразу при приёме | `site.photo` |
| **На подготовке (б/у)** — кнопка «Фото» у строки (Э12) | iPhone | после чистки/ремонта | `site.photo` |
| **Раздел «Сайт» → «Без фото»** (п. 14) | iPhone, ноутбук | обход витрины: список всех б/у, которых нет на сайте только из-за фото | `site.photo` |
| **Справочник → модель → цвет → «Фото модели»** (Э24) | ноутбук | фото для новых запечатанных (Д5) | владелец, админ |
| **Аксессуар → «Фото»** (Э24) | ноутбук, iPhone | | `site.photo` |

### 3.2 Шаги на iPhone (б/у, главный сценарий)

1. Нижняя панель → «Скан» → камера наводится на IMEI (или ввод `PM-10517`) → открывается паспорт телефона.
2. Вкладка **«Сайт»** → большая кнопка **«📷 Добавить фото»**.
3. Открывается встроенная съёмка ERP (страница с камерой через браузер, PWA): квадратная рамка-направляющая 1:1, подсказка по порядку кадров: **1 — перед (экран выключен), 2 — зад, 3 — левый бок, 4 — правый бок, 5 — экран включён (белый фон), 6 — дефект крупно (если есть)**. Кнопка «Снять» — без выхода из экрана, кадры копятся лентой снизу. Кнопка «Из галереи» — выбрать уже снятые (можно несколько).
4. «Готово» → фото загружаются сразу, по одному, в фоне; индикатор «Загружено 3 из 5». Если сеть пропала — загрузка продолжится сама, когда сеть вернётся (фото держатся в памяти страницы; при закрытии вкладки — предупреждение «2 фото ещё не загружены»).
5. Лента фото во вкладке: перетаскивание меняет порядок, первое фото — **главное** (метка «Главное»). Удалить — значок корзины → «Удалить фото?» → «Удалить».
6. Если галочка «Показывать на сайте» уже включена (по умолчанию она включена при приходе — п. 4.4), **больше ничего нажимать не нужно**: после обработки первого фото телефон появляется на сайте. Если выключена — включить переключатель «На сайте».
7. Вверху вкладки статус: «На сайте с 16:13 · Открыть» или «Не на сайте: нет цены — [Указать]».

**Итог:** в типичном случае 3 нажатия — Скан → Сайт → Добавить фото (снять) → Готово. Время до появления на сайте — п. 8.4.

### 3.3 Обработка на сервере (очередь `storefront-media`)

Шаги для каждого загруженного файла:

1. Проверка: тип JPEG / PNG / HEIC / WebP, размер ≤ 25 МБ, сторона ≥ 800 px. Иначе ошибка под фото: «Фото слишком маленькое (600 px). Снимите ближе или выберите оригинал».
2. Оригинал сохраняется в **приватную** папку `/<organization_id>/media/originals/` (не доступна из интернета). HEIC с iPhone конвертируется.
3. Поворот по EXIF, затем **удаление всех метаданных** (геолокация, модель камеры, дата).
4. Автоулучшение (Допущение, п. 3.4).
5. Нарезка WebP (качество 80, Допущение) в публичную папку со **случайным именем** файла (без кода товара, без фирмы — раздел 03, п. 5):

| Размер | Ширина | Где используется | Цель по весу |
|---|---|---|---|
| `xl` | 1600 px | увеличение фото в галерее карточки | ≤ 250 КБ |
| `lg` | 1000 px | галерея карточки на телефоне и ноутбуке | ≤ 120 КБ |
| `md` | 600 px | карточка в списке каталога (srcset) | ≤ 60 КБ |
| `sm` | 300 px | список на телефоне, поиск, подсказки | ≤ 25 КБ |
| `og` | 1200×630 JPEG | превью ссылки в WhatsApp, Instagram, Telegram (п. 13.1) | ≤ 150 КБ |

Допущение: JPEG для `og`, потому что не все мессенджеры показывают WebP в превью. Сайт работает в Chrome 109 и Safari iOS 15+, оба показывают WebP — отдельного JPEG для страниц не нужно.

6. Расчёт «качества кадра» (п. 3.5): тёмное, размытое, слишком мелкий телефон в кадре — только предупреждение.
7. Событие «фото готово» → задача пересборки карточки (п. 8). Публикуется только **обработанное** фото; пока обработка не закончена, в ERP у фото значок «обрабатывается».

Цель: от окончания загрузки до готового WebP — до 10 секунд на фото (Допущение, сервер 4 ядра).

### 3.4 Автоулучшение, обрезка и светлый фон

Допущение: ниже — разумный объём. Всё делается **на нашем сервере в РК**, без внешних сервисов; оригинал всегда сохраняется, любое улучшение можно отменить.

| Обработка | Когда | По умолчанию | Отменить |
|---|---|---|---|
| Выравнивание яркости и баланса белого | всегда | вкл | переключатель «Без обработки» у фото |
| Обрезка до квадрата 1:1 по рамке съёмки | всегда | вкл; если фото из галереи не квадратное — обрезка по центру с полями | ручная рамка «Обрезать» (сдвиг и масштаб пальцами) |
| **Светлый фон** (замена фона на однотонный светло-серый `#F3F4F6`) | только по кнопке «Светлый фон» у фото или галочке «Делать светлый фон для всех новых фото» в настройках сайта | **выкл** на старте | «Вернуть оригинал» |
| Автообрезка по контуру телефона (телефон по центру, поля 8%) | вместе со «Светлым фоном» | | «Вернуть оригинал» |

Правила «светлого фона»:
- Делается открытой моделью вырезания фона на сервере в очереди с низким приоритетом (Допущение: 5–20 секунд на фото; если сервер занят кассой — позже).
- Меняется **только фон**. Сам телефон, царапины и сколы не ретушируются никогда — для б/у это вопрос честности и возвратов.
- Если модель не уверена в контуре (рваный край), фото остаётся с исходным фоном и пометкой «Не удалось убрать фон — снимите на однотонном фоне».
- Совет в настройках: снимать на белом листе A3 — результат лучше любой автообработки.

### 3.5 Модерация фото

| Кто загрузил | Экземпляр уже на сайте? | Что происходит |
|---|---|---|
| Владелец, админ, старший продавец (есть `site.visibility`) | любой | фото сразу публикуется после обработки |
| Продавец (есть только `site.photo`) | нет | фото сохраняется; показать телефон на сайте продавец не может — включит владелец/админ (П4, 03 п. 55) |
| Продавец | да | Допущение: новое фото публикуется **сразу**, но попадает в список «Сайт → Новые фото» на просмотр; владелец может «Убрать» одним нажатием. Альтернатива «сначала проверка, потом сайт» — настройкой (вопрос 3) |

Автоматические подсказки (не блокируют, показываются под фото и в «Новые фото»):
- «Похоже, на фото видна наклейка с IMEI или экран „Об устройстве“» (Допущение: распознавание 15 цифр на фото текстовым распознаванием на сервере; при срабатывании фото **не публикуется**, пока человек с `site.visibility` не нажмёт «Проверил, IMEI не видно»). Это единственный блокирующий случай.
- «Фото тёмное / размытое» — по яркости и резкости.
- «Меньше 3 фото — добавьте ещё, с фото продают быстрее» (П4.1).
- «Главное фото — не перед телефона» — нет, такую проверку не делаем (Допущение: ненадёжно).

### 3.6 Фото новых запечатанных телефонов

- Берутся с **модели + цвета** в справочнике (архитектура Д5). При переносе из sfon фото моделей забираются из Open API ([`00-sfon-paritet.md`](00-sfon-paritet.md), п. 10).
- Справочник общий для фирм (Д1), поэтому фото модели общее. Фирма может заменить его своим (галочка «Своё фото для фирмы») — тогда видит только она.
- Если у модели нет фото нужного цвета — берётся фото модели в любом цвете с подписью цвета словами, и в ERP модель попадает в список «Сайт → Без фото» с пометкой «нет фото цвета Desert».
- Можно добавить к новому экземпляру своё фото (например, «живое» фото коробки) — тогда своё идёт первым, фото модели — после.
- Временные фото GSMArena из макетов на сайт **не берём** (дизайн README, «Временное»).

### 3.7 Хранение и удаление

- Удалённое фото пропадает с сайта при следующей пересборке карточки (≤ 60 с), файлы лежат ещё 30 дней (П4.2, Допущение), потом удаляются ночной задачей.
- Фото проданного б/у остаются 180 дней (страница «Продан» и история в паспорте), потом публичные размеры удаляются, оригинал — по сроку хранения фирмы (Э26).
- Ограничение: до 12 фото на экземпляр (Допущение).
- Все действия с фото пишутся в историю экземпляра и в журнал действий (03, «Цены и сайт»).

## 4. Видимость: на сайте / скрыт

### 4.1 Формула

Экземпляр виден на сайте, только если **все** условия выполнены (П4.1, дополнено):

| # | Условие | Если не выполнено, в ERP пишется |
|---|---|---|
| 1 | Статус `в наличии`, `в резерве` или `забронирован по заказу` (02, 10.1) | «Не на сайте: статус „На подготовке“» |
| 2 | Галочка экземпляра «Показывать на сайте» включена | «Скрыт вручную (Кайрат, 09.11 14:20)» |
| 3 | Модель не скрыта | «Скрыта модель iPhone 11 — [Открыть]» |
| 4 | Бренд / семейство не скрыто | «Скрыт бренд Xiaomi» |
| 5 | Категория (тип) не скрыта | «Скрыта категория Планшеты» |
| 6 | Магазин не скрыт с сайта и у магазина не выключено «показывать б/у» / «показывать новые» (как в sfon, [`00-sfon-paritet.md`](00-sfon-paritet.md), п. 8) | «Магазин скрывает б/у» |
| 7 | Розничная цена > 0 | «Нет цены — [Указать]» |
| 8 | Есть хотя бы одно готовое фото (у нового подходит фото модели) | «Нет фото — [Добавить]» |
| 9 | Себестоимость внесена (П4.1 п. 6) | «Нет себестоимости — спросите владельца» |
| 10 | Госбаза не «Не верифицирован» / «Заблокирован» (П5) | «Заблокирован в госбазе» |

Отсутствие отметки госбазы **не** скрывает телефон (сайт не продаёт — продажа на кассе всё равно потребует проверку, П5). На карточке просто нет значка «Проверен» (Допущение).

Причины считаются в одном месте (функция «почему не на сайте») и используются везде: вкладка «Сайт» паспорта, колонка «Сайт» в Э8 (подсказка при наведении), фильтр «не на сайте из-за…», раздел «Сайт».

### 4.2 Уровни переключателей

| Уровень | Где переключается | По умолчанию | Право |
|---|---|---|---|
| Экземпляр | паспорт → «Сайт»; массово в Э8; в приходе | см. 4.4 | `site.visibility` (п. 55) |
| Аксессуар | карточка аксессуара | вкл | `site.visibility` |
| Модель | Справочник → модель → «На сайте» | вкл | `site.rules` (п. 59) |
| Бренд / семейство | Справочник | вкл | `site.rules` |
| Категория (тип) | Справочник / «Сайт → Категории» | Смартфоны, Планшеты, Часы, Наушники, Аксессуары — вкл; прочие — выкл (Допущение) | `site.rules` |
| Магазин | Настройки → магазин: «Показывать на сайте», «Показывать новые», «Показывать б/у» | всё вкл | `site.rules` |

| Событие | Что делает система сама | Что делает человек |

| Новый | вкл | фото модели есть, ничего делать не надо |

## 6. Цены, старая цена, акции

### 6.1 Цена на сайте = цена в кассе

- На сайте показывается **розничная цена экземпляра из ERP**. Отдельной «цены для сайта» нет (Допущение: иначе клиент приходит с ценой с сайта, а касса пробивает другую — конфликт). Цена для Kaspi-магазина — отдельное поле позже (03, п. 53, этап 9).
- Любая смена цены — документ смены цены (П22) с историей «было → стало». Сайт обновляется сам.
- Скидка продавца на кассе (по лимиту роли) на сайт не влияет и не видна.
- Курс $ на цены сайта не влияет: цены покупателю только в ₸ (Д6). Если владелец пересчитал розницу по курсу (П, раздел 01 «курс») — это документ смены цены, сайт обновится.
- Формат: `489 000 ₸` (пробел-разделитель тысяч — неразрывный, знак ₸ после пробела). Без копеек.

### 6.2 Старая (зачёркнутая) цена

| Правило | Значение |
|---|---|
| Поле | «Цена до скидки» у экземпляра / варианта; заполняет владелец (03 п. 51) или акция (6.3) |
| Показ | только если больше текущей цены; иначе игнорируется без ошибки |
| Подсказка при снижении цены | в документе смены цены галочка «Показать прежнюю цену зачёркнутой» → поле заполнится прежней ценой |
| Честность | Допущение: если прежняя цена действовала меньше 7 дней, система предупреждает: «Цена 519 000 ₸ была всего 2 дня. Показывать её зачёркнутой рискованно» (требования к рекламе скидок в РК — не проверено) |
| Срок | необязательная дата «Показывать до»; после — поле очищается ночью |
| Метка «Скидка» | ставится сама, если есть старая цена; процент «−6%» считается и округляется вниз |

### 6.3 Акции

Акция — способ поменять цены многим товарам на время, не нарушая правило 6.1.

| Поле | Тип | Пример |
|---|---|---|
| Название ru / kk | текст | «Чёрная пятница» / «Қара жұма» |
| Период | дата-время с / по | 27.11.2026 00:00 – 30.11.2026 23:59 |
| Товары | фильтр: категория / бренд / модель / вариант / новый-б/у / конкретные коды | все новые iPhone 15 |
| Скидка | % или сумма ₸ или фиксированная цена | −5% |
| Округление | вниз до 1 000 / до 100 / без (Допущение: по умолчанию до 1 000 вниз) | |
| Показывать старую цену | галочка | да |
| Баннер | ссылка на баннер (п. 12) | |
| Метка на карточке | текст ru/kk | «Black Friday» |

**Как работает:**
1. Владелец создаёт акцию → «Предпросмотр»: таблица «код, было, станет, себестоимость (по праву), маржа станет» и предупреждение по каждой строке, где цена ниже себестоимости: «PM-10482: 464 000 ₸ < себестоимости 470 000 ₸».
2. «Запланировать». В момент начала планировщик проводит **документ смены цены** «Акция „Чёрная пятница“» (П22) по всем попавшим товарам. Новые экземпляры, оприходованные во время акции и подходящие под фильтр, получают акционную цену при проведении прихода (Допущение).
3. В момент окончания — документ возврата цен: каждому экземпляру ставится цена, которая была до акции, **если её не меняли вручную** во время акции. Если меняли — строка попадает в список «Решите сами» в уведомлениях владельца.
4. Касса продаёт по той же цене, что на сайте, — автоматически.

**Пример.** iPhone 15 Pro 256, 489 000 ₸, акция −5% → 464 550 → округление до 1 000 вниз → **464 000 ₸**, зачёркнуто 489 000 ₸, метка «−5%». 01.12 в 00:00 цена сама вернулась к 489 000 ₸.

Права: создать акцию — `price.bulk` (03 п. 52) + `site.content` (п. 58).

`платёж = вверх_до_целого_тенге( цена × (1 + переплата%) / срок )` для **главной** программы и **максимального** срока, который разрешён для этой цены.

| Цена | Программа | Показ |
|---|---|---|
| 489 000 ₸ | Kaspi, 24 мес, 0% | **от 20 375 ₸ × 24 мес** |
| 219 000 ₸ | Kaspi, 24 мес, 0% | от 9 125 ₸ × 24 мес |
| 589 000 ₸ | Kaspi, 24 мес, 0% | от 24 542 ₸ × 24 мес (24 541,67 → вверх) |

- В карточке — блок «Рассрочка»: выбор срока кнопками 3 / 6 / 12 / 24, платёж пересчитывается на странице без запроса к серверу; список программ, если их несколько; мелкая строка «Условия банка, не является офертой. Окончательное решение — банк» (Допущение: формулировку проверить у юриста).

## 8. Синхронизация ERP → сайт

### 8.1 Схема

```
Документ в ERP (продажа, приход, смена цены, фото, переключатель…)
   │  в той же транзакции базы пишется строка в storefront_outbox
   │  (что изменилось: unit 10482 / variant 412 / model 77 / store 1 / banner 5)
   ▼
Диспетчер (раз в 1 с) читает outbox → ставит задачи в очередь Redis «storefront»
   ▼
Задача «пересобрать карточку PM-10482 целиком из склада»
   │  читает текущее состояние, проверяет формулу 4.1, считает рассрочку, фото, порядок
   ▼
storefront_listings: вставить / обновить / пометить «продан» / удалить
   ▼
Сброс кэша по меткам: карточка, страницы категорий/модели/главной, где она была
   ▼
Сайт отдаёт новую версию
```

### 8.2 Почему так (правила для разработчика)

| Правило | Что значит |
|---|---|
| **Outbox в транзакции** | Событие пишется в таблицу `storefront_outbox` **внутри** транзакции проведения документа (02, п. 11: задачи ставятся после транзакции — outbox это и обеспечивает). Если Redis в этот момент недоступен, событие не теряется: диспетчер отправит его позже. Допущение: это уточнение «очереди Redis» из архитектуры 4, не замена |
| **Пересборка целиком, а не «дельта»** | Задача не применяет «цена стала X», а читает экземпляр заново. Поэтому порядок задач и повторы не важны: последняя всегда даёт правильный результат |
| **Идемпотентность** | Повторный запуск той же задачи ничего не ломает |
| **Склейка** | Несколько событий одного экземпляра за 2 секунды склеиваются в одну задачу (уникальный ключ задачи `unit:10482`) |
| **Приоритеты** | `storefront-high`: продажа, резерв, снятие резерва, скрытие, блокировка госбазы. `storefront`: цена, фото, описание, порядок. `storefront-low`: справочник, магазин, массовые операции, ночная сверка |
| **Массовые изменения** | Смена справочника/модели/магазина ставит задачи по каждому затронутому экземпляру пачками по 200 |
| **Повторы при ошибке** | 5 попыток: через 5 с, 30 с, 2 мин, 10 мин, 1 ч. После — запись в «Сайт → Состояние» и уведомление интегратору |
| **Сайт не пишет в склад** | Никогда. Единственная запись сайта — анонимные заявки и счётчики (п. 11) |

### 8.5 Гонка «клиент пишет о телефоне, который только что продали»

Сайт ничего не продаёт, поэтому двойной продажи через сайт быть не может (защита — на кассе, архитектура 2.7). Остаётся неудобство: клиент нажал WhatsApp за 10 секунд до продажи.
- Продавец вставляет код из сообщения в поиск ERP → видит «Продан 18:05, Айдар» и **кнопку «Похожие в наличии»** (та же модель ± память/цвет, те же условия б/у) → отправляет клиенту ссылки (кнопка «Скопировать ссылки для WhatsApp»).
- Страница «Продан» на сайте сама показывает похожие (п. 9.9).

### 8.6 Ночная полная сверка

Каждую ночь в 03:30 (Допущение: вне работы магазина и после ночной копии базы):

1. Таблица строится заново в теневую копию `storefront_listings_next` прямо из склада по формуле 4.1.
2. Сравнение с текущей: какие коды лишние, каких нет, у каких отличаются цена / статус / фото / магазин.
3. Подмена таблиц одной операцией (сайт ни секунды не пустой).
4. Сброс всего кэша сайта, перестроение `sitemap.xml`.
5. Отчёт: «Расхождений 0» → только запись в журнал. Если расхождения есть → запись в журнал и уведомление интегратору (архитектура, «Ночная сверка»). Если расхождений больше 10 — уведомление и владельцу: «Сайт ночью исправил 14 карточек. Интегратор уже знает».
6. Здесь же: снятие истёкших закреплений, старых цен, удаление файлов фото старше срока, страницы «Продан» старше 30 дней → `noindex` (п. 9.9).

### 8.7 Если что-то сломалось

| Ситуация | Что происходит | Что видит владелец |
|---|---|---|
| Redis / очередь упали | ERP и касса работают; сайт показывает последнее состояние; outbox копит события; после восстановления всё догоняется | «Сайт → Состояние»: «Сайт отстаёт на 12 минут» (красным, если > 5 мин) + уведомление интегратору |
| Пул «витрина» перегружен (атака, наплыв) | касса не тормозит (отдельный пул, архитектура 4); сайт отвечает из кэша, лишние запросы получают «Слишком много запросов» | — |
| Ошибка пересборки одной карточки | 5 повторов, затем она в списке ошибок | «Не удалось обновить PM-10482: …» — у интегратора |
| Сервер выключен | сайт недоступен | мониторинг (архитектура) |

Название, фото магазина, адрес ru/kk, ориентир, часы по дням, телефон (кнопка «Позвонить»), WhatsApp, Instagram, кнопки «Маршрут в 2ГИС» / «Яндекс Карты» / «Google Maps» (ссылки), реквизиты продавца (ИП, БИН — из настроек; Допущение: на сайте магазина реквизиты нужны — не проверено). Разметка `Store` для Google (п. 13.2). Если магазинов несколько — список карточек магазинов.

### 9.9 Страница «Продан»

- Тот же адрес `/phone/PM-10517`: фото, название, плашка **«Продан»**, цены нет, кнопок покупки нет.
- Блок «Похожие в наличии» крупно + кнопка WhatsApp «Подберите мне похожий» (текст с кодом проданного).

- После 30 дней: `noindex`, убрана из карты сайта (архитектура 4).
- После 180 дней (Допущение): постоянное перенаправление (301) на страницу модели; фото удаляются (п. 3.7).

### 9.10 Trade-in (заявка)

Цель — привести человека в магазин или WhatsApp с уже понятным телефоном, **не собирая персональных данных на сайте** (архитектура 4).

Шаги на странице:
1. «Что сдаёте?» — бренд → модель (поиск) → память → цвет (необязательно).
2. «Состояние»: экран (целый / царапины / трещина), корпус (как новый / следы / сколы), батарея (≥ 90 / 80–89 / < 80 / не знаю), Face ID / Touch ID работает (да/нет), был ли ремонт (да/нет/не знаю), комплект (коробка, да/нет).
3. «Что хотите взамен?» — необязательно: ссылка на товар с сайта (если пришёл с карточки, подставляется сам) или «пока не знаю».
4. **Предварительная оценка:** если у фирмы заполнена сетка цен скупки (П7, раздел 01: базовая цена модели минус скидки за дефекты) и включена галочка «Показывать оценку на сайте» — показывается диапазон «Ориентировочно 140 000 – 165 000 ₸. Точная цена — после осмотра в магазине». Если сетки нет или модель не в сетке — «Оценим в WhatsApp за 5 минут». Допущение: по умолчанию оценка на сайте **выключена**, пока Кайрат не заполнит сетку (00-analogi п. 13 — онлайн-предоценка «позже»).
5. Кнопка **«Отправить в WhatsApp»** → создаётся анонимная заявка `СЗ-…` (п. 11), открывается WhatsApp с готовым текстом (п. 10) — человек сам дописывает и отправляет, может приложить фото в WhatsApp.
6. Под кнопкой: «Что взять с собой: удостоверение личности, телефон с выключенным iCloud / Google-аккаунтом, зарядку» (тексты — «Сайт → Страницы»).

Фото телефона на сайте не загружаются (Допущение: чтобы не хранить чужие файлы с возможными личными данными; фото — в WhatsApp).

### 9.11 Гарантия, обмен и возврат

Текст из «Сайт → Страницы»; шаблон по умолчанию — из текста гарантийного талона фирмы (00-sfon-paritet п. 7) и правил возврата ([`00-kazakhstan.md`](00-kazakhstan.md), п. 8). Шаблон помечен для юриста: сроки возврата для онлайн-продаж и перечень невозвратных товаров — **не проверено**. Страница обязательна (00-kazakhstan, п. 8).

### 9.12 Политика конфиденциальности

## 11. Заявки с сайта в ERP

### 11.1 Принцип

Архитектура 4: «сайт без входа и без форм с персональными данными». Поэтому **заявка с сайта анонимна**: в ней нет имени и телефона. Связь с человеком появляется в WhatsApp, а продавец переносит её в ERP по **коду заявки** из сообщения. Это закрывает право 03 п. 60 «Заявки с сайта» без сбора персональных данных на сайте.

### 11.2 Что хранится — `site_leads`

| Поле | Пример |
|---|---|
| Номер | `СЗ-2041` (префикс «СЗ» — сайт-заявка, нумерация фирмы, как документы 01 п. 0.1) |
| Тип | вопрос по товару / рассрочка / бронь / похожий / под заказ / trade-in |
| Товар | `PM-10482`, цена на момент нажатия 489 000 ₸ |
| Данные формы | для trade-in — ответы п. 9.10 и оценка; для «под заказ» — запрос |
| Магазин | куда ушёл WhatsApp |
| Язык | ru / kk |
| Откуда пришёл | страница, метки рекламы `utm_*` (если есть), «прямой / Google / Instagram» по адресу перехода |
| Время | 09.11.2026 19:42 |
| Статус | `нажата` → `в работе` → `закрыта` |
| Кто взял, итог, ссылка на заказ/чек/акт, клиент | заполняется в ERP |

IP-адрес и данные браузера **не хранятся** (Допущение). Защита от накрутки — ограничение частоты по IP в памяти, без записи.

### 11.3 Работа продавца

1. Клиент пишет в WhatsApp: «… Код заявки СЗ-2041».
2. Продавец вставляет `СЗ-2041` (или `PM-10482`) в общий поиск ERP → открывается заявка: товар, его **текущий** статус («В наличии» / «Продан 18:05»), цена тогда и сейчас.
3. «Взять в работу» → заявка закреплена за продавцом.
4. Дальше одна из кнопок:
   - **«Забронировать»** → создаётся заказ П10 с этим товаром; телефон и имя клиента продавец вводит уже в ERP (с согласием, 03 «Согласие клиента», способ «WhatsApp»); на сайте — «Забронирован».
   - **«Продать»** → касса с товаром в корзине.
   - **«Trade-in»** → акт trade-in (П7) с заполненными моделью и состоянием.
   - **«Похожие»** → список похожих в наличии со ссылками для WhatsApp (п. 8.5).
   - **«Закрыть»** с итогом: купил (ссылка на чек) / не ответил / передумал / дорого / нет в наличии / другое.
5. Если продажа проведена с товаром из заявки в течение 7 дней — заявка закрывается сама с итогом «купил» (Допущение), продажа получает источник «Сайт».

### 11.4 Список «Сайт → Заявки»

- Вкладки: **В работе** · **Нажатые за сегодня** · **Закрытые**.
- «Нажатые» — все клики по кнопкам (многие люди нажимают и не пишут). Они не требуют действия и не шлют уведомлений (Допущение: иначе шум). Через 3 дня без работы — «не дошла», уходят в архив.
- Колонки: номер, тип, товар (фото, код, цена), статус товара сейчас, время, кто взял, итог.
- Права: `site.leads` (03 п. 60).

### 11.5 Статистика заявок (для владельца)

В «Сайт → Статистика» и в Статистике владельца (Э2) блок «Сайт за 7 дней»: просмотры карточек, нажатия WhatsApp, заявки взятые в работу, продажи с источником «Сайт», сумма продаж с сайта. Пример: «Просмотров 1 240 · WhatsApp 86 · в работе 31 · продаж 9 на 3 410 000 ₸».

### 11.6 Форма «Позвоните мне» (выключена)

Право 03 п. 60 упоминает «позвоните мне». Это форма с телефоном = персональные данные, что архитектура 4 на сайте не допускает. Поэтому форма **сделана, но выключена**; включает владелец в настройках только после того, как юрист дал текст согласия и политику (00-kazakhstan п. 2). При включении: поле телефона +7, галочка согласия (дата, версия текста сохраняются), без имени; заявка приходит push-уведомлением дежурным продавцам; телефон из заявки удаляется через 30 дней, если не стал клиентом (Допущение). См. вопрос 6.

- **hreflang** ru / kk / `x-default` = ru на каждой странице.
- **sitemap.xml** — разбит: страницы, модели, категории, товары; обновляется после ночной сверки и не чаще раза в час при изменениях; `lastmod` = последнее изменение карточки.
- **robots.txt**: закрыты `/search`, `/go/`, служебные адреса; адрес sitemap.
- Адреса только латиницей в нижнем регистре; старые адреса после переименования модели → 301 на новые (таблица перенаправлений хранится автоматически).

| Числа и цены | одинаково: `489 000 ₸`, «24 ай» в kk вместо «24 мес» |
| Закон о языках | обязательность казахского для ценников (ст. 21) к сайту — не проверено; делаем kk полноценным в любом случае |

«Сайт → Нет перевода» — список всего, где нет kk: модели/цвета справочника, описания товаров, баннеры, страницы, шаблоны. Кнопка «Заполнить» рядом с каждой строкой.

### 13.4 Скорость

| Показатель | Цель | Как |
|---|---|---|

### 13.5 Счётчики и статистика

- Свои счётчики без персональных данных (Допущение): просмотры карточек, нажатия кнопок (через `/go/`), поисковые запросы без результата. Хранятся агрегатами по дням в `site_stats` (товар, день, просмотры, клики), без IP.
- Сторонние счётчики (Яндекс Метрика, Google Analytics) — поле в настройках, по умолчанию пусто: они передают данные за пределы РК (00-kazakhstan п. 2 — локализация), решение за юристом (вопрос 11).
- «Сайт → Статистика»: топ просматриваемых, «смотрят, но не пишут» (просмотры > 50, кликов 0 за 14 дней — подсказка «проверьте цену/фото»), что ищут и не находят, заявки и продажи с сайта (п. 11.5).
